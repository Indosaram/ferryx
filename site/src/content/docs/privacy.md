This declaration explains how Ferryx handles your data, based on the implementation in the desktop application, remote gateway, and project website.

## Local-first operation

Ferryx stores your data on your own machine. Local terminal sessions, workspaces, Git worktree configurations, and application preferences remain stored on disk. When you connect to remote SSH hosts, workspace files and command execution remain on the remote host (`src-tauri/src/terminal/remote.rs:418-425`).

Local state lives in predictable paths:

- **Session and workspace layout:** The background daemon persists running sessions to disk:
  - Linux checks `$XDG_DATA_HOME/rorca/session_state.json` first, falling back to `~/.local/share/rorca/session_state.json` (`src-tauri/src/daemon/server.rs:925-930`). If neither base resolves, it composes `~/.rorca/rorca/session_state.json` (`:894-900,946-948`) or writes to the runtime directory (`:901-908`). Development builds use `rorca-dev` or `session_state.dev.json` (`:898-899,906-907`).
  - macOS defaults to `~/Library/Application Support/rorca/session_state.json` (`src-tauri/src/daemon/server.rs:917-920`).
  - Windows defaults to `%APPDATA%\rorca\session_state.json` (`src-tauri/src/daemon/server.rs:921-924`).
  - You can override the session directory using `FERRYX_SESSION_DIR` (`src-tauri/src/daemon/server.rs:418-421`).
- **Interface preferences:** Saved sidebar visibility, active workspace selections, and terminal font settings stay in webview or browser `localStorage` (`ui/src/lib/appShellPersistence.ts:8-27`, `ui/src/lib/terminalSettings.ts:91-99,102-109,321-328`).
- **Browsing history:** Embedded browser tabs record visited URLs locally in application storage only when `rememberBrowsingHistory` is enabled (`ui/src/lib/browserHistory.ts:28-35,91-96,170-176`). You can toggle this setting off, which also clears the saved history list, at any time (`ui/src/components/settings/BrowserSection.tsx:323-333`). Clearing this list doesn't erase webview cookies or external site profile data.
- **SSH connections:** Configured SSH hosts live in the platform application data directory under `com.ferryx.app/ssh_hosts.json` (`src-tauri/src/ipc/ssh.rs:194-209`, `src-tauri/src/daemon/server.rs:1995-2007`), or under `FERRYX_DATA_DIR/ssh_hosts.json` if set. On Linux, this resolves to `$XDG_DATA_HOME/com.ferryx.app` or `~/.local/share/com.ferryx.app`.
- **Runtime files:** On Unix, the runtime directory (`/tmp/ferryx-<UID>`, with the legacy `/tmp/rorca-<UID>` also served for one release) resolves from the process real UID via POSIX `libc::getuid` (`src-tauri/src/daemon/server.rs:543-554,561-571`), created with 0700 permissions (`:1090-1123`). The canonical daemon socket (`daemon.sock`) is validated and secured with 0600 permissions (`:5702-5706`). Unix agent sockets (`agent-state.sock`) apply best-effort 0600 permissions without halting startup on error (`:4460-4462`). Windows builds bind a loopback TCP listener and record the port in `daemon.port` (`:654-657,5679-5699`). These permissions restrict access to your local user account against unprivileged local users, without preventing root or administrative access.

- **Diagnostic logs:** In headless daemon mode, agent activity release reasons (`manual_reset`, `foreground_agent_to_shell`) are recorded, alongside other daemon info-level events and panic and signal records, to a bounded local log file at `~/.ferryx/logs/daemon.log` or `$FERRYX_DATA_DIR/logs/daemon.log` (`src-tauri/src/daemon/logging.rs:15,55,67-75,124-139,215-234,258-262,274-290`). This log is created with 0600 permissions, bounded to a maximum of 1 MiB (clearing the file when the next record would exceed that limit), and fed through a non-blocking 256-record queue. The agent activity release records carry only session identifiers, previous activity states, and release triggers, without terminal output or command history.

Terminal output stays in an in-memory ring buffer with a default capacity of 512 KiB per session (`src-tauri/src/terminal/output_hub.rs:8,813-816,357-362`). Monotonic sequence numbers let reattaching clients catch up on retained chunks without writing raw terminal streams to persistent logs (`src-tauri/src/daemon/server.rs:6639-6650,8941-8945`). Chunks evicted past the buffer capacity can't be replayed, and this in-memory buffer doesn't prevent running tools or agents from keeping their own logs.

## Zero desktop telemetry

The desktop application and the project website are separate: the sections below describe the app, and [Website analytics](#website-analytics) describes the site. The desktop app contains no analytics of any kind, and nothing on the website changes that.

Inspecting `src-tauri` and `ui` source code confirms the absence of desktop analytics tooling:

- Product dependency manifests contain no metrics SDKs such as Sentry, PostHog, or Google Analytics (`src-tauri/Cargo.toml:99-275`, `ui/package.json:21-76`).
- The desktop shell Content Security Policy permits local dev endpoints, internal IPC, and hardcoded `ferryx.dev` relay domains (`src-tauri/tauri.conf.json:30`). It doesn't dynamically adapt to arbitrary custom relays, nor does it govern native Rust requests or external webviews.
- Software update checks: In native desktop builds, Ferryx periodically queries GitHub release metadata on startup and on an hourly schedule (`ui/src/App.tsx:419-421`, `ui/src/lib/updater.ts:149-153,168,360-385`). When an update is downloaded, the updater verifies the artifact signature against the configured public key (`src-tauri/tauri.conf.json:35-39`, `src-tauri/src/ipc/updater.rs:143-144,455-456`). Builds running from `WindowsApps` paths skip these updater checks (`src-tauri/src/ipc/updater.rs:63-79`), leaving delivery to the Microsoft Store.

## Website analytics

This section covers `https://ferryx.dev` only. The desktop application is unaffected by every choice described here and sends no analytics either way.

The website can use Google Analytics 4, and only with your explicit permission:

- **Off until you choose:** The page ships an inert `<template>` with the consent choice and nothing else. No Google script is requested, no `dataLayer` is created, and nothing is written to `localStorage` before you press a button (`site/src/lib/analyticsRuntime.ts:112-132,218-225`, `site/src/components/SiteAnalytics.astro:112-122`).
- **Equal choice, reversible:** "Allow analytics" and "Decline analytics" are the same control with the same styling and size. Your answer is stored under `ferryx.site.analytics-consent` in `localStorage`, and an "Analytics choice" button at the end of every page reopens the panel so you can change your mind. Withdrawing consent sets `ga-disable-<measurement id>` and sends a `denied` consent update, which stops further measurement for the page (`site/src/lib/analyticsRuntime.ts:207-225,234-238`).
- **Declining costs you nothing:** Every part of the site behaves identically with analytics declined.
- **Builds without an ID measure nothing:** The tag only exists when the site is built with a valid `PUBLIC_GA_MEASUREMENT_ID` (format `G-XXXXXXXXXX`). Local development builds, forks, and previews without that variable ship no consent panel and make no Google requests (`site/src/lib/analytics.ts:53-57`, `site/src/components/SiteAnalytics.astro:11,112-122`).

When you allow analytics, the site records:

- **`page_view`:** Sent once per page load, replacing the automatic page view so the reported URL can be sanitized first (`site/src/lib/analyticsRuntime.ts:184,197-204`).
- **`download_click`:** Sent when you click a release artifact link (including `.dmg`, `.exe`, `.AppImage`, `.deb`, and versioned `ferryx-cli` artifacts), with the parameters `platform`, `asset_id`, `destination`, and `link_location` (`site/src/lib/analytics.ts`). Microsoft Store links count as a Windows install intent; the menu offers the Store as the Windows download and lists the GitHub `.exe` installer only for releases that publish it. Opening the GitHub releases listing page is not recorded as a download.

What is deliberately not collected:

- **URL query strings:** Before any measurement is sent, the page URL is rebuilt with only the campaign parameters `utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content`, and `utm_id`. Every other query parameter is discarded, so search terms, e-mail addresses, or tokens that ride along in a link never reach Google (`site/src/lib/analytics.ts:19-26,88-102`).
- **Advertising and cross-site signals:** Consent defaults deny `ad_storage`, `ad_user_data`, `ad_personalization`, and `analytics_storage`; accepting grants `analytics_storage` only. The tag is configured with `allow_google_signals: false` and `allow_ad_personalization_signals: false` (`site/src/lib/analyticsRuntime.ts:164-169,185-186,190-195`).
- **Outbound link rewriting:** Download links are never rewritten with tracking parameters; the URL you click is the URL in the page.

Google Analytics receives the request metadata any web request carries, including your IP address, which Google uses for coarse geolocation before discarding it, and a first-party cookie identifier set only after you accept. Clearing site data for `ferryx.dev` removes both the cookie and your stored choice, and the panel will ask again.

A self-hosted, cookieless analytics script is also supported for forks: it renders only when both `PUBLIC_ANALYTICS_SRC` and `PUBLIC_ANALYTICS_DOMAIN` build environment variables are set (`site/src/components/SiteAnalytics.astro:107-111`). Neither variable is required by, nor related to, the Google Analytics path above.

Search engine verification meta tags (`google-site-verification`, `msvalidate.01`) render only when `PUBLIC_GSC_VERIFICATION` or `PUBLIC_BING_VERIFICATION` are set at build time (`site/src/components/SiteAnalytics.astro:105-106`). They are static ownership tokens and collect nothing.

## Remote gateway and network modes

Remote access lets you monitor or control terminal sessions from another device. The gateway starts Off by default (`src-tauri/src/remote/state.rs:53-60`). You can enable it through network configuration, or by requesting a pairing code, which auto-configures and starts Relay mode if the gateway was Off (`src-tauri/src/daemon/server.rs:7211-7229`). Persisted non-Off configuration restores automatically when the daemon starts (`:5761-5765`).

Four network modes determine connection behavior:

- **Off:** The gateway shuts down its listener and aborts active relay tasks (`src-tauri/src/remote/server.rs:7819-7838`, `src-tauri/src/daemon/server.rs:8512-8518`). Turning off the gateway stops remote listening, but it doesn't block independent outbound client traffic such as SSH sessions, embedded browser tabs, or background updater queries.
- **LocalNetwork:** Ferryx binds port 43821 on loopback, and on a selected network interface only after the explicit insecure opt-in described below or when that address is a verified Tailscale overlay (`src-tauri/src/remote/server.rs:7965-7970,7981,7996-8007,8032`, `src-tauri/src/remote/state.rs:22,702-718,726-737`). Resolution prefers a usable route-probe address, which can be public even when another interface has a private address. Paired devices can access protected session endpoints, while health, UI assets, and pair exchange routes remain unauthenticated (`src-tauri/src/remote/server.rs:376,5444-5452,7456,7469`). Direct connections use plain HTTP and WebSockets over TCP (`:7851-7853,8003-8006`).
- **Tailscale:** The daemon binds port 43821 to loopback and the first interface address in the CGNAT range `100.64.0.0/10` that also passes an active-overlay check (`src-tauri/src/remote/state.rs:111-114,166-170,739-744`, `src-tauri/src/remote/server.rs:7965-7970,7981,8032`). The check asks the Tailscale CLI whether the address belongs to the local node; without that proof it fails closed on macOS and Linux, while Windows falls back to matching a Tailscale adapter in `ipconfig /all` output (`src-tauri/src/remote/state.rs:238-279,286-345`). It doesn't verify authenticated tailnet membership of other peers; restricting access relies on network firewall rules and Tailscale ACLs. WireGuard transport encryption is handled by Tailscale, not Ferryx TLS.
- **Relay:** The daemon opens an outbound WebSocket to a relay server, defaulting to `https://relay.ferryx.dev` (`src-tauri/src/remote/state.rs:20`, `src-tauri/src/remote/relay_client.rs:541,582-587`). Connections use TLS encryption when directed to secure `https://` or `wss://` endpoints, while custom `http://` or `ws://` endpoints run unencrypted and are accepted only for loopback hosts or, with the insecure-relay opt-in, private RFC1918 hosts; public plaintext relays are rejected (`:945-998`).

The gateway listener never binds to the wildcard `0.0.0.0` address (`src-tauri/src/remote/server.rs:7965-7970,7981`). Operators deploying a custom relay should set `relayUrl` in persisted `remote-config.json` for deterministic restoration across restarts, because `FERRYX_RELAY_URL` is only read during pairing auto-configuration or IPC fallback (`src-tauri/src/daemon/server.rs:7215-7219,7264-7268`, `src-tauri/src/remote/server.rs:7931-7940`, `src-tauri/src/ipc/remote.rs:389-398`).

## What leaves your machine during remote access

Enabling remote access exposes specific workspace data to paired devices. Traffic through the default relay uses TLS (`src-tauri/src/remote/relay_client.rs:975-976,1006-1008`). For direct LAN connections without a reverse proxy, the internal server listens on plain HTTP and WebSockets, and a non-overlay LAN listener is only bound after an explicit insecure opt-in (`src-tauri/src/remote/server.rs:7851-7852,7868-7871,8001-8007`). Operators on untrusted networks should place a TLS-terminating proxy in front of the port.

Authorized remote clients receive:

- **Workspace metadata:** Project names, worktree branch labels, session identifiers, and optional titles (`src-tauri/src/remote/protocol.rs:273-279,283-299`, `src-tauri/src/remote/server.rs:622-649,785-790`). Process names are not sent as dedicated metadata fields.
- **Desktop context:** Identifiers for the active workspace, worktree, session, and tab, without a separate pane identifier (`src-tauri/src/remote/protocol.rs:218-233`).
- **Terminal output:** Live text, ANSI escape codes, snapshots, and recent chunk buffers from running sessions (`src-tauri/src/remote/server.rs:2824-2830,2847-2857`).

Client permissions govern available actions:

- **Keystrokes and input:** Raw text chunks sent to active PTY processes require Control permission (`src-tauri/src/remote/server.rs:2902-2908,3414-3420`).
- **Window geometry:** Terminal resize events require Control permission, and resize requests from View clients are ignored (`src-tauri/src/remote/server.rs:1970-1971,2933-2935,3458-3460`). The server gates resize commands on control permissions in the text and grid handlers.
- **Control signals:** Interrupt signals (VINTR byte 0x03) require Control permission (`src-tauri/src/remote/server.rs:2947-2952,3476-3481`, `src-tauri/src/terminal/session.rs:1354-1357`), directing SIGINT through the PTY line discipline to the foreground process group rather than guaranteeing child process termination.
- **Worktree actions:** Creating or removing Git worktrees requires Control permission (`src-tauri/src/remote/server.rs:1645-1650,1691-1696`).

Clients paired with View permission have input keystrokes discarded (`src-tauri/src/remote/server.rs:2902-2908,3414-3420`), but can still revoke their own tokens (`:1735-1740`). The gateway HTTP router exposes routes for session streaming and metadata, plus directory and repository browsing endpoints and a byte-range read of host files, all of which require a Machine-scope Control device (`:7461-7468,7600-7604`, `src-tauri/src/remote/filesystem.rs:480-482`, `src-tauri/src/remote/repo_discovery.rs:453-455`, `src-tauri/src/remote/workspace_api.rs:292-296`), and Control sessions can execute arbitrary shell commands inside terminals.

Remote gateway endpoints accept and store web push subscription payloads in memory (`src-tauri/src/remote/server.rs:3741-3753`, `src-tauri/src/remote/push.rs:29-33,74-77`). The codebase currently includes no dispatching caller to send push notifications to external notification services.

## Pairing codes, tokens, and credentials

Pairing authorizes access to protected session endpoints (`src-tauri/src/remote/server.rs:7625-7629,1757-1761`). Public endpoints like health, static assets, and pair exchange do not require tokens (`:7456,7469,5444-5451`), and pairing alone doesn't encrypt plain LAN transport.

Defensive layers protect pairing credentials:

- **Machine identity:** The host generates a unique machine UUID and an Ed25519 keypair lazily on the first pair exchange, identity lookup, or Relay startup (`src-tauri/src/remote/auth.rs:76-109`, `src-tauri/src/daemon/server.rs:6747-6749`, `src-tauri/src/remote/server.rs:411,3931-3946,7765-7767`). These reside in `identity.json`. Hostname discovery queries `PATH` with fallback to "Ferryx machine" (`src-tauri/src/remote/auth.rs:88-99`). Unix writes set 0700 parent and 0600 file permissions (`:1630-1637,1656`), without retroactively updating permissions on read (`:76-84`). Windows relies on inherited filesystem ACLs.
- **Pairing PINs:** Local pairing generates a 6-digit PIN between 100000 and 999999 (`src-tauri/src/remote/auth.rs:724-725`), while relay pairing generates zero-padded codes from 000000 to 999999 (`src-tauri/src/remote/relay_client.rs:193`). Each PIN expires 60 seconds after creation, or 600 seconds for machine-scope codes (`src-tauri/src/remote/auth.rs:264,270-276`). Active PINs and relay pairing capabilities are included in best-effort saves to `remote-auth.json` (`src-tauri/src/remote/auth.rs:791-817,1408-1415,1430-1434`). Expiry rejects use; it does not guarantee immediate disk erasure, and failed saves can leave older records.
- **Rate limiting:** Failed pairing attempts are counted per source and in total in a budget window (`src-tauri/src/remote/auth.rs:278-281,472-475,540-558`). After 5 failures from one source, or 50 overall, subsequent attempts return HTTP 429 until the window closes (`src-tauri/src/remote/server.rs:428-439`). This failure budget is persisted with the pairing codes, so a restart doesn't reset it (`src-tauri/src/remote/auth.rs:586,639,1413`).
- **Device tokens:** Successful pairing mints a 64-character alphanumeric bearer token (`src-tauri/src/remote/auth.rs:382-388,985`). Approved devices and tokens are stored in `remote-auth.json` (`:1408-1415`). Clients store the token in browser or webview `localStorage` (`ui/src/lib/remoteClient.ts:44-52`).
- **Socket tickets:** Connecting to WebSockets can use a short-lived single-use ticket minted by an authenticated client (`src-tauri/src/remote/server.rs:257,306-315,325-339`, `src-tauri/src/remote/state.rs:853-854`), avoiding long-lived tokens in query strings.
- **Expiration and revocation:** Inactive devices expire after 30 days of inactivity (`src-tauri/src/remote/auth.rs:287,1119-1121`). Re-pairing an existing installation replaces and revokes its previous bearer tokens (`:977-994`). Revoking a device removes its tokens and signals its active WebSocket streams to terminate (`:1297-1308`, `src-tauri/src/remote/server.rs:1801-1808,5205-5207`).

Credential storage on Linux and macOS resolves under `~/.ferryx/remote/` (`src-tauri/src/cli.rs:2167-2168`, `src-tauri/src/remote/auth.rs:61-63`). Windows installations place credentials in `%LOCALAPPDATA%\Ferryx\remote\` or `%USERPROFILE%\.ferryx\remote\` (`src-tauri/src/cli.rs:2158-2162`, `src-tauri/src/remote/auth.rs:53-57`). Operators can override this directory using `FERRYX_DATA_DIR` (`src-tauri/src/cli.rs:2152-2154`, `src-tauri/src/remote/auth.rs:48-50`). Missing directories are created automatically on write (`:1630-1632`). Pairing state remains memory-only only when no per-user base directory can be resolved from the environment (`:44-66`), in which case the CLI returns an error if run without `FERRYX_DATA_DIR` (`src-tauri/src/cli.rs:2171-2173`).

## External services and tools

Ferryx connects to external servers in several operational contexts:

- **Remote SSH sessions:** Outbound SSH connections connect to configured remote hosts (`src-tauri/src/ssh/bridge.rs:937-949`).
- **Relay connections:** In Relay mode, the daemon establishes an outbound connection to the relay server (`src-tauri/src/remote/relay_client.rs:523,541`).
- **Direct-path STUN lookups:** When two paired machines try the opportunistic direct path, each daemon resolves and queries public STUN servers to learn its public UDP address. The defaults are `stun.l.google.com:19302` (Google) and `stun.cloudflare.com:3478` (Cloudflare) (`src-tauri/src/paired_host/direct_connect.rs:34` (`DEFAULT_STUN_SERVERS`), `src-tauri/src/remote/direct_api.rs:58` (`configured_stun_servers`)). The connecting machine queries them before it sends a direct offer; the host queries them only after an offer has passed authentication, trust, and signature checks (`src-tauri/src/paired_host/direct_connect.rs:279` (`discover_public_endpoint`), `src-tauri/src/remote/direct_api.rs:314` (`stun_servers`)). Each STUN server sees the machine's public IP address and UDP port, and your DNS resolver sees the lookup; no terminal data goes to them. Set `FERRYX_STUN_SERVERS` to a comma- or space-separated list of your own `host:port` servers (IPv4 address or hostname; the direct path is IPv4-only), or to `off` to stop the lookups on that machine. The direct path needs both sides, so a machine with STUN off starts no direct attempt, answers direct offers with `DIRECT_DISABLED`, and keeps its sessions on the relay (`src-tauri/src/paired_host/direct_connect.rs:39` (`STUN_SERVERS_ENV`), `src-tauri/src/paired_host/direct_client.rs:52` (`configured_stun_servers`), `src-tauri/src/remote/direct_api.rs:252` (`DIRECT_DISABLED`)). A malformed value stops the daemon at startup with an `invalid FERRYX_STUN_SERVERS entry` error (`src-tauri/src/cli.rs:3811` (`configured_stun_servers`)).
- **Software updates:** Direct native desktop builds query GitHub release metadata on an hourly schedule (`src-tauri/tauri.conf.json:35-38`, `ui/src/App.tsx:419-421`, `ui/src/lib/updater.ts:360,373-389`). Executables running from `WindowsApps` paths skip updater checks (`src-tauri/src/ipc/updater.rs:63-79`), leaving updates to the Microsoft Store.
- **Coding agents:** CLI tools like Claude Code, Codex, or custom agents execute as terminal child processes or report status via local sockets (`src-tauri/src/daemon/server.rs:1636-1642`). Their network traffic, credential use, and API communications depend on their own tooling and provider configurations.
- **Embedded web views:** Navigating to an external URL inside a browser tab loads assets from that site (`src-tauri/src/ipc/browser.rs:2266-2272`). Remote sites receive standard HTTP request details and set cookies under their own policies.

Setting the gateway mode to Off does not block SSH connections, external web views, updater queries, or the STUN lookups this machine makes when it connects to a paired host.

## Relay and account data

This section covers what the relay (`ferryx-relay`) and the account service it hosts keep on the operator's server, for example `relay.ferryx.dev`. If you never use Relay mode or a Ferryx account, none of it exists for you. Where the code has no expiry, the retention is listed as "kept until account removal": nothing deletes it until an operator removes it on request.

- **Machine ownership:** The relay binds each machine ID to the Ed25519 public key that first enrolled it, and writes that map to `machine_keys.json` (`src-tauri/src/remote/relay_server.rs:987-988`). The default path is `~/.ferryx/relay/machine_keys.json`, or `FERRYX_RELAY_DATA_DIR`/`FERRYX_RELAY_KEY_FILE` when set (`:596-607`). The account service also records each enrolled machine (machine ID, display name, platform, public keys, enrollment and last-seen times) in its `machines` table (`src-tauri/src/account/store_sqlite/schema.rs:133-145`). Retention: kept until account removal.
- **Billing state:** Account and billing records live in the SQLite store `account-store.sqlite3` (`STORE_SQLITE_FILENAME`, `src-tauri/src/account/store_sqlite/mod.rs:10,39`). Billing tables hold the plan, seats, host packs, status, end date, the Lemon Squeezy customer ID and portal URL (`subscriptions`), the grace and stop timestamps (`billing_states`), and a SHA-256 hash, name, and outcome for each received webhook (`payment_events`) (`src-tauri/src/account/store_sqlite/schema.rs:172-203`). Retention: kept until account removal; `payment_events` rows contain no account identifier and have no expiry.
- **Peer IP addresses:** The relay reads the connecting TCP peer address (`peer_ip`, `src-tauri/src/remote/relay_server.rs:3745-3746`, defined at `:3779-3782`) to rate-limit connection and pairing attempts. These counters are kept in memory per IP (`:539-540`) and dropped after a 60-second window or lockout ends (`:567`, `:996-1001`). The relay code does not write peer IPs to disk or to its own log lines; the hosting provider or a reverse proxy in front of the relay can keep its own access logs. Separately, the account service stores the requester IP taken from `cf-connecting-ip` or `x-forwarded-for` on each pending machine request (`src-tauri/src/account/machine_requests.rs:114-128,275`). Retention: the request's 15-minute lifetime plus 7 days (`src-tauri/src/account/machine_requests.rs:22`, `src-tauri/src/account/store.rs:19,356-358`).
- **Email address and code hashes:** Signing in stores your email address in the `users` table (`src-tauri/src/account/store_sqlite/schema.rs:101-105`) in the account data directory (`docs/account-service.md:29`). Login codes, pairing capabilities, and session bearers are stored only as hashes (`docs/account-service.md:63-64`). Retention: the email address is kept until account removal. Sessions expire after 30 days and login codes after 10 minutes (`src-tauri/src/account/store.rs:13-14`). Expired sessions are purged on the next store write (`:359`); a login code row is removed when the app collects its session or when an expired code is presented (`src-tauri/src/account/service.rs:885,897`). Login emails go out through Resend when the operator configures `RESEND_API_KEY` (`src-tauri/src/account/mailer.rs:429-435`), so Resend receives the address and the message.
- **Payment processor:** Paid plans are sold through Lemon Squeezy, which handles checkout, quantity changes, and webhooks (`docs/account-service.md:124-127`). Checkout sends Lemon Squeezy your account ID and, when known, your email address (`src-tauri/src/account/billing/lemonsqueezy.rs:1265-1269,1281-1288`). Card and invoice data stay with Lemon Squeezy and never reach the Ferryx account service. Retention: Ferryx keeps only the `subscriptions` fields listed above, until account removal; Lemon Squeezy keeps its records under its own policy.

Ferryx has no self-service account deletion. To have your account data removed, send a request through the private reporting channel listed in [`SECURITY.md`](https://github.com/Indosaram/ferryx/blob/main/SECURITY.md) from, or naming, the email address on the account. The operator then deletes the records by hand, following the "Account data deletion requests" steps in `docs/billing-operations.md`: cancel any subscription, remove your user, sessions, machines, and billing rows from `account-store.sqlite3`, remove your machine IDs from the relay's `machine_keys.json`, and ask Lemon Squeezy to delete the customer record.

## Your choices and data deletion

You retain control over the data Ferryx stores:

- You can change or withdraw the website analytics choice at any time using the "Analytics choice" button at the end of any page on `https://ferryx.dev`. This affects the website only; the desktop application never sends analytics.
- You can stop remote access by switching the gateway mode to Off (`src-tauri/src/remote/server.rs:7819-7839`, `src-tauri/src/daemon/server.rs:8512-8523`). This stops the listener and aborts relay tasks, using graceful shutdown that doesn't forcibly sever active local WebSocket streams immediately.
- You can stop this machine's third-party STUN lookups by starting its daemon with `FERRYX_STUN_SERVERS=off` (set it on each machine to stop them all); sessions to and from that machine then stay on the relay. You can instead point the lookups at STUN servers you run (`src-tauri/src/paired_host/direct_connect.rs:48` (`stun_servers_from`)).
- Paired devices can be revoked through the desktop settings interface (`ui/src/components/settings/RemoteAccessSection.tsx:252-263`) or HTTP API (`src-tauri/src/ipc/remote.rs:440-457`, `src-tauri/src/remote/server.rs:1723-1746`). The CLI tool lets you list and approve pairings (`src-tauri/src/cli.rs:2097-2102,2187-2212`), but doesn't include a revoke command, and generating a pairing code there now only reports that an account login is required.
- Clearing browsing history removes the application history list (`ui/src/lib/browserHistory.ts:102-111`, `ui/src/components/settings/BrowserSection.tsx:328-331`), but doesn't erase webview cookies or site storage.
- To remove persistent state, stop any running Ferryx processes first, then delete local paths according to your platform:
  - Linux: `~/.local/share/rorca` (or `$XDG_DATA_HOME/rorca`), `com.ferryx.app` app data (containing SSH hosts), `~/.ferryx` (containing remote auth, machine identity, and remote config), `/tmp/ferryx-<UID>` (runtime socket and locks), the legacy `/tmp/rorca-<UID>` (also served for one release), and legacy `~/.rorca` if present (`src-tauri/src/daemon/server.rs:543-553,561-570,894-899,927-929,946-948,1999-2001`, `src-tauri/src/remote/auth.rs:61-63`).
  - macOS: `~/Library/Application Support/rorca`, `~/Library/Application Support/com.ferryx.app` (SSH hosts), `~/.ferryx`, `/tmp/ferryx-<UID>`, and the legacy `/tmp/rorca-<UID>` (`src-tauri/src/daemon/server.rs:543-553,561-570,894-899,919,1999-2001`, `src-tauri/src/remote/auth.rs:61-63`).
  - Windows: `%LOCALAPPDATA%\Ferryx` (remote auth), `%APPDATA%\rorca` (sessions), `%APPDATA%\Ferryx` (persistent lock), `%APPDATA%\com.ferryx.app` (SSH hosts), `%USERPROFILE%\.ferryx`, and `%LOCALAPPDATA%\Ferryx\runtime` (`src-tauri/src/daemon/server.rs:633-646,857-858,894-899,923,1999-2001`, `src-tauri/src/remote/auth.rs:53-56`).
  - Custom overrides: Check any directories configured by `FERRYX_DATA_DIR` (`src-tauri/src/cli.rs:2152-2154`, `src-tauri/src/remote/auth.rs:48-50`, `src-tauri/src/daemon/server.rs:848,943,1996-1997`, `src-tauri/src/daemon/logging.rs:215`), `FERRYX_SESSION_DIR` (`src-tauri/src/daemon/server.rs:418-422`), or `FERRYX_RUNTIME_DIR` (`src-tauri/src/daemon/server.rs:544-546`).
  - Web storage: Clear webview or browser `localStorage` (`ui/src/lib/storageKeys.ts:46`, `ui/src/lib/remoteClient.ts:7-13`) to purge interface preferences and cached client tokens. Clearing site data for `ferryx.dev` also removes the website analytics choice stored under `ferryx.site.analytics-consent` and any Google Analytics cookie set after you accepted.
  - This cleanup list is non-exhaustive. External assets like Git worktrees created inside project directories (`.orca-worktrees`), shell command logs, and browser profile cookies remain subject to their own storage locations.
