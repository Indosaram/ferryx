## Deliberate divergences from the pinned reader

1. **`rowKey` is resolved by the caller, not the planner.** The pinned `AnswerStep` is
   `{ keys?, text?, pick? }`, and `pick` is replaced at execution time by
   `(seen as ParsedPrompt).rowKey` — the key the *fresh* screen names for the row the moves
   ended on (`prompt.ts:2786`). This port returns `ReferenceCodexAnswerStep::Pick` for those
   steps and exposes `codex_model_row_key` so the executor resolves it on its own read. The
   frozen wire DTO `ReferenceKeyStep` has no `pick` form, so `reference_key_steps` **refuses**
   a step list containing one rather than dropping it or guessing a key.
2. **The internal parse is returned beside the public card.** `answerKeys` reads
   `selectedIndex`, `customMenuIndex`, `rejectWithEscapeIndex`, `optionSteps` and `rowKey` off
   `parsedByPublicPrompt`, a `WeakMap` the pinned module keeps privately. None of those fields
   is on `InteractivePrompt`, and `ReferenceAnswerPlanner`'s only input is the public
   `ReferencePrompt`. `parse_reference_codex_prompt` therefore returns `ReferenceCodexPrompt`
   (the frozen card plus that view) and `plan_reference_codex_answer` plans from it. This is
   the reason this lane satisfies the contract's `ReferencePromptDetector` alias and not its
   `ReferenceAnswerPlanner` alias; the dispatcher (task 9) owns the planner-shaped entry point.
3. **The prompt id is recomputed, not carried.** The pinned `finishPrompt` hashes
   `JSON.stringify({agent, ...input, ...hashed})` with the fields in that object's own order
   and takes 12 hex characters. `codex_prompt_id` reproduces that ordering and
   `JSON.stringify`'s escaping by hand, because the reference's hash must be stable for equal
   cards and different for any change it would see — including a body change past the
   12 000-character display cap. No fixture pins a literal id; the tests pin the *relations*
   (a cursor move keeps it, a command change or a beyond-cap change does not).
4. **`comparable` does not normalize NFKC.** `sameText` normalizes before stripping
   non-alphanumerics (`prompt.ts:2523`). This port strips and lowercases only: no Unicode
   normalization crate is a dependency of this crate, and adding one is a manifest-level
   decision, not a family lane's. Full-width and compatibility forms therefore compare unequal
   here where the reference compares them equal. This affects only the collapsed-queue
   `QueueFront` match (`queued-collapsed.txt`), which is ASCII in the pinned capture.
5. **The negative lookahead is spelled out.** `queuedQuestionCount`'s last guard is
   `/^›\s(?!\d+\.)/`, and the `regex` crate has no lookahead. `is_queue_main_prompt` splits the
   prefix and tests `/^\d+\./` on the remainder, which is the same predicate. It is the only
   pinned pattern in this lane that is not compiled verbatim.
6. **`codex-queued-question` has no `promptTailIsActive` arm.** Upstream has none either — the
   card is never produced by the screen parse — so the arm this port carries is unreachable and
   exists only to keep the match exhaustive.
7. **`fallback-menu` / `fallback-keys` are not ported here.** `parseFallbackPrompt`
   (`:2122-2178`) is the dispatcher's last resort for a pane no reader knows; it is not a Codex
   responder and belongs to task 9. Only `codexModelListWaits`, which that card must consult,
   is ported.
8. **The rollout scan is not ported.** `unansweredCodexQuestions` (`server/codex.ts:477`) reads
   and tails a file; the resolver (task 3) owns path resolution and the read. This lane takes
   the questions as `ReferenceCodexQueuedQuestion` values.
