- **Orca runs structured native chat on paired Remote Server workspaces** — Orca
  - Orca's release notes for v1.4.220 and v1.4.221 (opened) describe structured chats that open on the paired Orca server owning the workspace: a Stop that really ends Claude or Codex including subagents, mid-turn messages held as editable cards that can be Steered into the running turn, subagent work in its own section, and journal-backed history; the same notes call Remote Server experimental with Remote Server 2.0 due that week, while the README documents SSH worktrees with auto-reconnect and a headless Linux server guide for orca serve. Compared with Ferryx's user workflow, where a remote Linux machine is enrolled over an outbound relay and the phone or web client only streams a raw terminal grid, Orca now gives remote workspaces the same supervision as the desktop. The Ferryx gap is a chat/journal abstraction: agent state is inferred from titles and a manifest detector, with no queued follow-ups and no explicit permission-wait model. Scope is large for a full chat layer, but a narrow slice (queued follow-up messages plus an explicit needs-input state surfaced in paired sessions) is testable today against Ferryx's existing status pipeline.
  - source: https://github.com/stablyai/orca/releases (release notes)
  - source: https://github.com/stablyai/orca (official repository README)
  - verdict: SKIP — The terminal-only premise is outdated: ui/src/remote/RemoteApp.tsx renders MobileChatWorkspace, and agentConversation.ts maps transcript messages and tool results. RemoteApp still sends messages as PTY text and Stop as Ctrl-C, so reliable queued steering and subagent cancellation are genuine additional contracts, not a small status change. Permission screens already produce blocked states through agent_detect/manifests/claude.toml. Open PR #4 also modifies RemoteApp.tsx and remote/server.rs; skip overlapping work rather than schedule another remote-chat PR.
- **Orca mobile companion ships an iOS app and an Android APK for steering agents** — Orca
  - Orca's official README (opened) links an iOS App Store companion (orca-ide) and Android APK 0.0.52 so users can monitor and steer agents from a phone and get notified when an agent finishes; the releases page shows ongoing mobile engineering (RPC migration, attention boundaries moved off terminal panes, mobile performance fixes). Compared with Ferryx's workflow of QR/PIN mobile web pairing that streams a dependency-free DOM terminal grid, Orca now has store-distributed clients with native notification delivery. The Ferryx gap is notification and client parity: browser-only pairing cannot deliver iOS or Android push, so a finished agent is only noticed when the page is open or via desktop OS notifications. Scope for store apps is out of reach short term, but browser Web Push or relay-side alerts are a small, testable increment on the existing pairing gateway.
  - source: https://github.com/stablyai/orca (official repository README)
  - source: https://github.com/stablyai/orca/releases (release notes)
  - verdict: SKIP — Background delivery remains incomplete, but not absent scaffolding: ui/src/lib/pushSubscription.ts registers subscriptions and src-tauri/src/remote/push.rs stores them; searches found no production registration caller or actual push sender. Open PR #4 touches push.rs, server.rs and RemoteApp.tsx, while the working tree contains mobile capabilities, Apple generation files and mobile bootstrap changes. This overlaps active mobile work. Native apps plus push infrastructure also exceed one focused parity PR.
- **cmux turns Cloud Machines on for everyone in v0.65.0** — cmux
  - The cmux v0.65.0 release note (opened) says the Cloud tab is now shown by default in Settings and the right sidebar so every build can enable Cloud Machines, and the changelog (opened) details hosted VMs: per-VM browser origins without a system VPN, resource and token usage meters, team-scoped shared machines reachable concurrently by members, New Display remote desktops, and browser sign-in URLs redirected to the Mac. Compared with Ferryx, whose remote story is outbound-relay pairing of machines the user already provisioned with ferryx-cli --daemon, cmux now offers on-demand compute and team sharing inside the same window. The gap is provisioning, accounts and billing, none of which exist in the Ferryx repo; scope is very large and local testability is limited to mocking the machine list, so this is a strategic watch item rather than a parity task to schedule.
  - source: https://github.com/manaflow-ai/cmux/releases (release notes)
  - source: https://cmux.com/docs/changelog (official changelog)
  - verdict: SKIP — The claim that Ferryx has no accounts is incorrect: src-tauri/src/account/service.rs implements login, machine enrollment, ownership and machine listing. Those manage user-provided machines, not hosted compute. VM provisioning, tenancy, usage accounting and billing would introduce a hosted product with ongoing operational responsibilities, not one focused reviewable PR.
- **cmux moves a stopped Claude Code session between Mac and SSH host and tracks remote agent state** — cmux
  - The cmux changelog (opened) lists cmux session move with an SSH destination or local target, which carries a stopped Claude Code session's transcript, memory and git working tree between the Mac and an SSH host and resumes it there; it also reports Claude Code and Codex on a cmux ssh host as Running, Needs input or Idle in the sidebar with hooks installed on the host, keeps persistent cmux ssh sessions on cmux-tui for reconnect and restore, and adds Predictive Local Echo so keystrokes echo locally over slow links. Compared with Ferryx, where managed worktrees are machine-bound under .orca-worktrees/wt-<slug> on branches orca/<workspace-id>/<slug> and each remote machine is enrolled separately through the relay, there is no way to relocate an agent session with its transcript between desktop and remote, and remote panes carry no per-agent status over the relay. Scope is medium (worktree transfer plus transcript handoff), and it is testable with the headless Linux pairing Ferryx already ships.
  - source: https://cmux.com/docs/changelog (official changelog)
  - verdict: SKIP — SSH and remote status are not wholly missing: src-tauri/src/ssh/state_bridge.rs authenticates agent-state reports, ProjectDialogs.tsx supports SSH projects/worktrees, and remote/server.rs maps waiting/blocked attention. Moving transcript, agent memory and dirty Git state between machines is a distinct missing capability. It requires provider-specific relocation, compatibility checks and transactional recovery across hosts; combining that with predictive echo and status parity is not one focused PR.
- **cmux checkpoints scrollback and auto-continues agents after retryable errors** — cmux
  - The cmux changelog (opened) headlines crash-proof sessions: terminal scrollback is checkpointed, interrupted Claude sessions are recoverable with cmux session restore, and agents whose turn ends on a retryable error such as model capacity or a dropped connection are told to continue automatically under Settings > Automation > Auto-Resume Agents After Errors, while authentication and billing failures stay visible for the user. Compared with Ferryx's Resilient persistence claim (headless daemon, 512 KiB sequenced ring buffer, replay on reattach), Ferryx survives GUI crashes and relays but never resumes a turn: a dropped model connection leaves a pane sitting at a prompt that the manifest-driven detector can only mark as waiting. The gap is automatic agent continuation. Scope is small to medium if implemented through agent hooks, and it is testable by severing a model connection mid-turn and asserting the pane resumes with status still correct.
  - source: https://cmux.com/docs/changelog (official changelog)
  - verdict: BLOCKED — ui/src/lib/agentAutoResume.ts already schedules guarded, staggered reconnection of restorable agent sessions, but that is not continuation after a model error. The inspected code exposes screen-derived blocked states and transport retry classifications, not a verified provider-level distinction between retryable turn failures, authentication failures, billing failures and permission waits. Without that event contract and an acknowledged continuation mechanism, safe bounded auto-continuation cannot yet be judged as a small PR; screen text or a generic waiting state is insufficient.

Compared with Ferryx's remote pairing (6-digit PIN gateway, outbound relay, DOM terminal grid, desktop OS notifications only), Zeron offers native mobile push and cross-device steering while keeping sessions on the user's own machines. The Ferryx gap is push delivery and device-targeted session creation. Push needs Apple infrastructure and relay work, which is a large scope, while headless-versus-headless parity with ferryx-cli is already comparable and testable today.
  - source: https://github.com/zeronsh/zeron/releases (release notes)

  - verdict: SKIP — Device targeting already has substantial support: ProjectDialogs.tsx branches on local, SSH and pairedDaemon targets and creates worktrees through the corresponding adapters; account/service.rs provides enrolled-machine ownership and listing. This is not proof of MCP parity, but contradicts a blanket absence of device-targeted workflows. Push delivery remains incomplete despite subscription scaffolding, and its push/server/mobile paths overlap open PR #4 and current mobile changes. Native iOS push plus MCP session creation is not a focused incremental PR.
- **Bentomux raises agent approvals in an always-on-top overlay and mirrors panes to a phone over LAN** — Bentomux
  - The official Bentomux site I opened describes one native window where every tab reports idle, working or blocked by reading the process and terminal screen, permission prompts are captured by a unix-socket hook bridge and raised in an always-on-top overlay with Approve, Deny and Jump to tab, 22 agent CLIs are detected on PATH without wrapping them, workspaces keep their PTY and scrollback across app quit and machine restart, and an optional QR-paired monitor serves panes and states to a phone on the local network. Compared with Ferryx, which does the same job with manifest-driven status detection, notifications and a relay-backed mobile web grid, Bentomux attacks the same stuck-agent pain point with explicit approval capture. The gap is approval handling: Ferryx only infers waiting-for-input from titles, so a prompt in an unfocused pane can stall. Scope is medium (hook bridge plus overlay) and it is testable by driving Claude Code's permission prompt through the existing status pipeline.
  - source: https://bentomux.takora.dev/ (official site)
  - verdict: BLOCKED — The title-only premise is false: agent_detect/manifests/claude.toml contains Bash and generic permission rules, independent_probe.rs exercises permission screens, and remote/server.rs exports waiting/blocked attention. A correlated Approve/Deny mechanism is a real additional capability, but the inspected daemon has no permission-request/response contract. Adoption needs evidence for request identity, authenticated responses, expiry, provider cancellation and portable Windows transport before an overlay can safely answer prompts. A Unix-socket marketing description does not establish that contract.
- **Emdash runs the same parallel-worktree workflow on remote machines over SSH and SFTP** — Emdash
  - Emdash's official repository and site (both opened) describe local projects plus remote machines over SSH and SFTP with agent, key, password and OpenSSH-certificate authentication stored in the OS keychain; marker-tagged entries are installed into agent user-level configs so status, notifications and resumable sessions work while staying inert outside Emdash; and issues from Linear, Jira, GitHub, GitLab, Asana and more are pushed into isolated worktrees for review, PR creation and merge. Compared with Ferryx, whose differentiator is outbound relay pairing that needs no SSH, open ports or public IP, Emdash covers the same remote-parity need through the mainstream SSH path and adds ticket intake Ferryx lacks. Gap: no issue-tracker intake, and only one remote transport. Ticket intake is a medium integration and an SSH transport beside the relay is a small to medium addition, both testable against any existing SSH host.
  - source: https://github.com/generalaction/emdash (official repository)
  - source: https://emdash.sh/ (official site)
  - verdict: SKIP — SSH projects already exist in src-tauri/src/ssh/projects.rs, worktree.rs and state_bridge.rs, with SSH selection and remote worktree creation wired through ui/src/components/ProjectDialogs.tsx. Issue intake is the useful missing slice, but it is adopted once under github-copilot-app-parallel-sessions below. Do not create a duplicate integration or add another SSH transport.
- **GitHub Copilot app bundles parallel worktree sessions, cloud sessions, Canvases and Agent Merge** — GitHub Copilot app
  - The official github/app repository I opened describes an agent-native desktop app for Windows, macOS and Linux where each local session runs in its own isolated git worktree while cloud sessions keep running in GitHub-hosted environments that can be picked up from any device; Canvases expose plans, terminals, browser previews, diffs and workflow state as shared inspectable surfaces, My Work aggregates sessions with issues and pull requests, Automations turn repeatable prompts into scheduled or background tasks, and Agent Merge carries pull requests through review, checks and merge conditions. Compared with Ferryx's workflow (worktree per agent, split native panes, manifest status detection, relay remote machines), GitHub now ships orchestration plus PR landing inside one control center backed by its own infrastructure. The Ferryx gap is ticket-to-worktree intake, scheduled automations and merge orchestration; PR and automation work is medium scope through GitHub's API, and the nearest testable slice is pulling an issue straight into a new worktree pane.
  - source: https://github.com/github/app (official repository)
  - verdict: ADOPT — Adopt only the proposed issue-intake slice. ProjectDialogs.tsx:AddWorktreeDialog accepts a manual slug/base ref and invokes existing creation adapters; src-tauri/src/ipc/worktree.rs:cmd_worktree_create delegates creation to the daemon. Searches of backend and UI source found no GitHub-issue intake path. A local-project issue lookup, preview and existing worktree-creation handoff reduces manual setup without adding an orchestrator. Open PRs #4–#6 and the two competitor worktrees do not implement this slice. This uses the remaining daily slot after the earlier navigator adoption; cloud execution, scheduling and Agent Merge are excluded.
