## Five source-confirmed findings (new local IDs, not ledger edits)

### GB-01 - Relay enrollment read/merge/write is not one cross-process transaction

CONFIRMED, conditional multi-instance deployment; authorization durability/ownership risk. `src-tauri/src/bin/relay.rs:91-93` constructs state -> `relay_server.rs:1578-1628` verifies signed control auth -> `:385-443` binds/persists key. Two processes sharing the same key-store path have distinct parking_lot mutexes. Both can read the same old file at `:408`, merge independently and each acknowledge enrollment after writing at `:440`. Last publication drops the first machine; conflicting first claims can both be admitted in their separate live instances.

Dependency checked: `src-tauri/src/remote/auth.rs:868-919` performs publication; its low-level StoreLock is Unix-only (`:837-866,879-880`) and even on Unix acquired AFTER the relay's read/merge. It cannot serialize the whole transaction. Windows has no such low-level lock. Distinct process temp names (`:884`) prevent shared temp collision, not lost updates. Do not confuse AuthManager's separate portable transaction (`auth.rs:736-765`, File::lock) with relay enrollment: bind_machine_key does not call it. Existing “concurrent” regression (`relay_server.rs:2747-2785`) calls first.bind then second.bind sequentially and cannot expose the race.

Alias: none in findings.md. Related auth-persistence review is not grounds to deduplicate this distinct relay caller. Recommend transaction ownership around reload/merge/publication, with post-lock conflict check; not merely a Windows rename workaround. Normal per-user ACL weakness or a deployed multi-process relay is NOT asserted.
