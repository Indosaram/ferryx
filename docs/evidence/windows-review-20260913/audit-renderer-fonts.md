## Confirmed findings (severity ordered)

### RF-01 - HIGH - GDI DIB pixels read before required flush
- Evidence: src-tauri/src/native_terminal/renderer/directwrite_raster.rs:165-178 issues TextOutW then immediately dereferences DIB memory; no GdiFlush declaration/call exists in this module/domain. Microsoft's CreateDIBSection contract explicitly requires GdiFlush before any use of its bits pointer following GDI drawing.
- Reachable chain: surface_host.rs:2630-2643 -> renderer surface viewport -> instances.rs:213-223 -> atlas.rs:230-251 -> rasterizer.rs:47-56 -> font_manager.rs:269-281 -> directwrite_raster.rs:168-170. Every uncached Windows glyph takes this path.
- Impact: coverage is sampled before batched drawing is guaranteed complete; missing/partial text is possible. Do not claim every Windows glyph is blank: batching/runtime decides manifestation. DIB initialization is also not explicit; allocation-content behavior is a separate unknown, not asserted as the cause.
- Failing-first proposal: narrow GDI adapter seam queues TextOut writes until Flush, then run the production raster path and assert the returned mask equals the queued raster; additionally real Windows raster probe compares A/W masks to an independently flushed reference with batching enabled. No sleeps or probabilistic stress-to-pass test.
- Binary observable: newly encountered ASCII/CJK glyphs have correct stable ink on their first presentation rather than requiring another draw. Smallest fix/write scope: directwrite_raster.rs plus Windows raster tests; flush and handle failed drawing before CPU readback, preserve cleanup.

### RF-02 - HIGH - Configured font stack is passed as one GDI face
- Evidence: font_manager.rs:56-72 retains the raw family; :269-281 forwards it unchanged; directwrite_raster.rs:115 and :144-159 pass it to CreateFontW. That API accepts one typeface name, maximum 32 UTF-16 units including NUL, not a CSS stack. This breaks preference lists even if all listed fonts are installed.
- Caller: cmd_terminal_apply_overrides in src-tauri/src/ipc/preferences.rs:136-149 -> rerender_native_sessions(:55-95) -> host render -> FontManager::global(:77-87) -> rasterizer. Ghostty imported families can also be comma-joined; this is not solely a frontend-default claim.
- Failing-first proposal: Windows adapter test with `Consolas, "Courier New", monospace` verifies selected face via GetTextFaceW equals the first installed requested family; test quoted names, unavailable first family and generic monospace mapping. Compare raster against explicit Consolas, not merely nonzero ink.
- Binary observable: settings family selection changes actual letter shapes to the selected installed font and preserves monospacing. Smallest scope: Windows face-stack parsing/resolution in directwrite_raster.rs (shared resolver only if needed by metrics) plus raster tests.
- Refutation: historical claim of guaranteed proportional MS Sans Serif is too strong: FIXED_PITCH | FF_MODERN is requested. The UI default stack has 38 UTF-16 units (39 including NUL), not the historical prose's stated raw length. Backend default is `monospace`, not that UI stack.

### RF-03 - HIGH - Cell geometry ignores the selected Windows font
- Evidence: font_manager.rs:119-136 always returns round(size*scale*0.6), round(size*scale*1.25), regardless of family; directwrite_raster.rs:144-168 independently selects/rasterizes a real font at a rounded pixel size, at top-left, without font metrics or a shared baseline.
- Chain: NativeTerminalPane.tsx:745-768 -> cmd_native_terminal_set_bounds -> surface_host.rs:2173-2176 -> derived_cell_metrics_for_scale -> composition.rs:182-225 -> terminal grid/PTY dimensions; the same guessed cell dimensions size each atlas bitmap and clip glyph ink.
- Failing-first proposal: real Windows font metrics probe for installed Consolas and Courier New at 13/17 px, scales 1/1.25/1.5/2; assert cell advance/height follow measured resolved font, and compare full g/M/box-line glyph bounding boxes with unclipped reference. Fixtures must prove their font metrics differ from the synthetic ratios.
- Binary observable: aligned box lines and no clipped ascenders/descenders after font/DPI change. Smallest scope: font_manager.rs and Windows raster metrics/baseline, plus Windows font tests. Historical top-left baseline claim is folded here, not counted as an independent guaranteed clipping bug for every font.

### RF-04 - HIGH - Font-family changes retain the old atlas and row cache
- Evidence: renderer/types.rs:194-203 has cell size/scale/theme but no font identity; renderer/renderer.rs:710-716 only clears atlas if that config changes. Windows metrics are identical for all families at a given size. atlas.rs:221-243 keys only text/bold/italic; row_cache.rs:32-50 reuses rows unless generation/hash changes.
- Reachable chain: preferences.rs:136-149 -> rerender_native_sessions(:55-95) -> surface_host.rs:2152-2207 constructs the same RendererConfig -> update_config -> row/atlas reuse. FontManager::global(:77-87) does rebuild the font manager, but cached glyphs bypass it.
- Failing-first proposal: isolated Windows process renders fixed ASCII in explicit font A, applies font B at unchanged size/theme/scale through preferences IPC, awaits the render completion, then compares the retained renderer pixels to a fresh renderer under B. Establish A and B reference masks differ before asserting equality to B. Also test size changes that round to the same metrics.
- Binary observable: existing terminal letters immediately switch with settings; old and newly emitted letters cannot use mixed families. Smallest scope: track font identity/revision at renderer invalidation (font_manager + renderer configuration/host integration as necessary), plus cache/IPC regression tests. This defect is in committed logic; foreign image additions did not introduce it.

### RF-05 - MEDIUM - Color emoji is categorically unavailable on Windows
- Evidence: color_glyph.rs:189-205 exports a non-macOS function returning None; font_manager.rs:170-181 tries it and :269-301 ends in Alpha on Windows. Colored atlas/pipeline support already exists, but Windows never produces Color.
- Caller: PreparedGlyph::new, atlas.rs:36-51 -> rasterizer.rs:47-56 -> FontManager candidate routing. Wide-cell classification is retained but cannot supply color/ZWJ shaping.
- Failing-first proposal: Windows FontManager test for Segoe UI Emoji cat and a supported ZWJ sequence asserts Color, expected buffer extent and unequal RGB channels on inked pixels, then offscreen integration verifies those colors survive atlas upload/compositing. Keep missing-font handling explicit.
- Binary observable: supported emoji render with native color instead of only foreground-colored silhouettes/tofu. Smallest scope: Windows color raster implementation + cfg export in color_glyph.rs and tests; extend secondary symbol routing only where coverage probe proves it necessary.

### RF-06 - MEDIUM - DPI-only cell-size changes do not reach Ghostty
- Evidence: surface_host.rs:1067-1102 and :1231-1255 call terminal.resize only when cols/rows change, then store new cell metrics regardless. NativeTerminal::resize (terminal.rs:391-420) is the path forwarding pixel cell dimensions. Ghostty's C resize (vendor/ghostty/src/terminal/c/terminal.zig:1458-1479) and Terminal.zig:4020-4051 explicitly support updating pixel geometry with unchanged grid.
- Chain: NativeTerminalPane DPI media-query change(:2051-2061) -> bounds IPC -> host.prepare_session_layout; render gets new metrics while Ghostty keeps prior width_px/height_px. Warm reattach has the same guard. Applies cross-platform, particularly monitor-DPI switches preserving grid dimensions.
- Failing-first proposal: host seam with 80x24 at 8x16 pixels, then same grid at 16x32 with corresponding physical bounds; inspect real Ghostty pixel geometry (or its cell-size report) and require 16x32. Repeat warm reattach. Register reply/render completion before triggering, bounded timeout only.
- Binary observable: pixel-size terminal queries agree with receipt cellWidthPx/cellHeightPx after DPI switch; foreign Kitty placements sized in cells remain aligned. Smallest scope: both host resize guards and equivalent attach/recovery pixel-geometry paths, plus host tests. Baseline defect predates foreign Kitty; images make the stale geometry more visible, not its origin.

### RF-07 - MEDIUM - Toasts remain behind the topmost terminal child HWND
- Evidence: platform/windows.rs:321-333 raises terminal HWND above WebView2. UI yielding selector in ui/src/lib/nativeTerminalVisibility.tsx:12-27 recognizes only dialog/search. ui/src/components/ui/sonner.tsx:50-79 mounts bottom-right Sonner; actual dependency emits section/ol, aria-live and data-sonner-toaster, no matching role (ui/node_modules/sonner/dist/index.mjs:1140-1165).
- Reachable caller: NativeTerminalPane.tsx:1019-1041 remote clipboard-image failure calls toast.error while a native terminal is visible; App also mounts global Toaster. A terminal covering bottom-right physically overlays this HTML regardless of CSS z-index.
- Failing-first proposal: Windows-platform visibility-hook integration mounts real Toaster, subscribes to visibility transition, emits a persistent error toast and asserts a non-occluded presentation policy; Windows HWND test intersects toast DOM bounds with terminal HWND bounds and confirms toast pixels in screenshot after exact present/DOM signals.
- Binary observable: full error toast and action/close controls visible over a terminal. Smallest scope: shared yielding policy plus tests (explicit visible toast selector/overlay registration); preserve terminal session while hidden. A DirectComposition redesign is not the smallest required fix. Coordinate with UI lane to avoid duplicate ownership.

### RF-08 - MEDIUM - Font tests deterministically assume the macOS raster stride
- Evidence: font_manager.rs:349-355 asserts width*height*4 for ASCII while Windows returns Alpha(width*height), :298-301. :449-455 indexes Alpha with RGBA stride. Integration repeats it in tests/native_terminal_renderer_contract/font_rasterization.rs:29-47.
- Reachable chain: test_font_manager_derives_nonzero_metrics_and_rasterizes / test_glyph_orientation_regression -> rasterize_glyph -> Windows Alpha. This is a provable assertion mismatch/index overrun, not an executed Windows failure in this review.
- Failing-first probe: on Windows run `cargo test --manifest-path src-tauri/Cargo.toml --lib test_font_manager_derives_nonzero_metrics_and_rasterizes -- --nocapture` and the corresponding renderer contract filter; expected first length mismatch is pixels vs 4*pixels. No runtime app symptom: blocks trustworthy cross-platform font validation.
- Smallest scope: font_manager test module and renderer font-raster contract tests; match RasterizedGlyph variants for length/coverage indexing, use isolated known fonts/preferences, retain meaningful glyph assertions rather than skipping Windows. Font-install-dependent density/PUA tests also need controlled fixtures, not timing retries.
