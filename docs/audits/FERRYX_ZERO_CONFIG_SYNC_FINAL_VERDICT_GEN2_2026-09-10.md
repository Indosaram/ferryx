## VERDICT: REQUEST CHANGES — NOT APPROVED

**The submission does not resolve every blocker in the previous verdict.** Several narrow fixes are verified: colon-scoped ticket targets, no-store/private caching and Clear-Site-Data stripping, rejection of short capabilities, rejection of unissued tokens once a machine's token cache is populated, and the previously failing SSH socket probe. A complete Rust remote-suite run reaches 158/158, the existing frontend suite passes 134/134, and the frontend builds.

However, the new direct-probe change releases the permanent device bearer before verifying the candidate's identity. The ticket check fails open before a machine's first exchange and again after relay restart; its cache also fails to track revocation and can deny still-valid older devices. Previously blocking daemon/CLI ownership, identity-store concurrency, generation-bound raw roles, bounded registration lifetime and authoritative settings remain unresolved. These are independently inspected or reproduced behaviors, not objections to commit labels or a requirement that every old defect remain unchanged.

**Do not release this revision as completing F01–F10.** Retain the verified repairs, correct the credential-release regression and authoritative admission model, and complete the prior acceptance criteria. Audit completion is distinct from release approval.

## 3. Remaining blocking findings

### 3.1 F04 — High: token-cache absence grants admission, and cache presence is not authoritative authorization

**Source:** `src-tauri/src/remote/relay_server.rs:137–157,194–228,578–615,835–879`; gateway authorization remains in `src-tauri/src/remote/server.rs:883–910,949–977`.

The decisive expression in `is_valid_device_token` is:

```rust
self.paired_tokens.lock().get(machine_id)
    .is_none_or(|tokens| tokens.contains(token))
```

The missing-entry case returns true. `paired_tokens` starts as a new in-memory map on each RelayState construction, independently of the persistent ownership store. Only a successful exchange observed by this relay populates it. No invalidation, revocation synchronization, expiry or reconstruction path exists for this set.

Independent public-HTTP observations establish all of the following:

| State | Request / observation | Result |
| --- | --- | --- |
| Online machine, before any pairing/cache entry | No bearer | 401 — retained protection |
| Same machine, no paired device | Never-issued bearer | **200 with a ticket** |
| Machine cache populated | Never-issued bearer / recorded bearer | 401 / 200 — narrow new repair |
| Reconstructed relay using the same ownership file | Same never-issued bearer | **200 again** |
| Cached real gateway device revoked in AuthManager | Gateway protected HTTP / relay ticket request | **401 / 200** |
| Older valid gateway token, then another token added to relay cache | Older token before / after population | **200 / 401**, although gateway still validates it |

Warm-cache observations invoke the trusted `register_device_token` method directly to isolate cache semantics; they are not represented as full pairing-UI E2E tests. The existing `coordinator_pairs_through_relay_to_real_gateway` test separately exercises successful exchange and the warm-cache 401/200 behavior. The before-pairing and restart checks use actual public HTTP routes and real authenticated control channels.

**Impact:** unauthenticated clients can still allocate from the global ticket budget and trigger later backend work while the cache is absent. Revoked clients can obtain tickets from stale entries; valid preexisting/local-paired clients can become unusable when another device populates the cache. The token set is also unbounded and retains bearer material without an eviction/authority lifecycle. The current ticket record lacks device permission and owning control generation; an unrelated Origin is not rejected by the tested admission path.

**Important boundary:** these observations do not prove unauthorized terminal access. An independent real RelayClient → actual gateway events test delivered an application event and then closed the browser stream after device revocation. The gateway remains the authenticating and revocation-enforcing authority. It is relay admission/cache coherence that is defective. Preserve the working backend checks.

**Required repair:** authorize issuance through the owning gateway or a synchronized, revocation-aware authority bound to the current machine/control generation. Missing or stale authority must not silently allow issuance. A simple change to `is_some_and` alone would leave restart and older-device availability broken; define bootstrap/recovery and migration explicitly. Bind purpose/options and device authority, test revocation plus restart, and add source/device/tenant budgets. Authentication, Origin validation and session invalidation are distinct controls [E2].

### 3.2 F09 — High regression: the proposed ownership probe discloses the credential it is supposed to protect

**Source:** `ui/src/remote/RemoteApp.tsx:443–487`; `ui/src/remote/zeroConfigSecurityProbe.test.tsx:120–141`; `ui/src/lib/directPathUpgrade.ts:44–62`; `src-tauri/src/remote/server.rs:147–151,196–201`.

The new Authorization header is part of the first candidate health request. Machine-ID comparison happens only after its response arrives. The browser therefore offers the permanent credential to every permitted candidate being probed, rather than only to a previously authenticated endpoint. A private-address allowlist and cookie omission do not establish possession of the paired machine's key.

Two controlled frontend tests mount the actual RemoteApp, hold the health response unresolved, and inspect the outgoing request. Both observe `Authorization: Bearer <synthetic victim token>` **before any response or machine identity is supplied**. One candidate later reports the wrong machine ID; the other returns HTTP 401. Both are refused for subsequent transport use, but the secret was already included in the health request. This is precisely the excluded request in the submitted test's later `directCalls` filter.

This proves the application's credential-release decision, not live LAN interception. Actual delivery remains conditional on browser network/CORS/TLS policies allowing the request. Those conditions cannot substitute for the missing machine identity check: a permitted hostile endpoint can receive a request, and a later mismatch or HTTP error cannot retract it. HTTP candidates remain accepted by the normalization helper where browser policy permits them.

The actual health handler takes no Authorization input and returns only `status` and `version`. Loopback probes with no bearer and with an invalid bearer both receive 200 with no `machineId`. Thus the changed frontend fixtures invent an authenticating health contract the server does not implement. A matching public ID is also not proof of the paired machine key. Sending a bearer authenticates its presenter; it does not demonstrate that the recipient is entitled to receive it. RFC 6750 explains bearer possession and the need to protect against disclosure and validate the intended server/channel [E1].

**Required repair:** do not send device credentials in candidate discovery. Establish an encrypted channel authenticated to the already paired machine identity before credential release; otherwise retain relay transport. Returning or comparing a public machine ID, requiring a header from the client, or making the health mock return 401 without that header does not supply that proof. Add a negative regression requiring no Authorization on an unverified candidate's first request. Direct/legacy event and terminal query credentials and daemon-derived settings readiness remain unresolved as in section 4.

### 3.3 F07/F08 — High: capability syntax does not bound lifetime or establish monotonic registration ownership

**Source:** `src-tauri/src/remote/relay_server.rs:431–470,1229–1287`; `src-tauri/src/remote/relay_client.rs:74–126`.

The new capability length/character checks are real. The relay nevertheless only requires `expires_at` to be in the future; it does not impose the coordinator's sixty-second maximum. A valid 32-hex capability with expiry **86,400 seconds ahead** receives a Ready ACK in the independent loopback test. Replaying the exact registration is rejected rather than acknowledged idempotently. A distinct registration with generation 1, after accepting generation 2 on the same control connection, is also acknowledged Ready with generation 1. The optional client generation is echoed, not enforced as an immutable owner sequence.

The same-process coordinator has useful local ACK/expiry guards, but these are not the relay's registration/control ownership guarantees. Five registrations per caller-chosen machine do not bound total public registry cardinality, fleet guessing, aggregate source prefixes or tenant-fair ticket/session consumption. These previously required admission and lifecycle contracts have not been implemented.

**Required repair:** impose a relay-side maximum original lifetime, preserve authoritative monotonic deadlines, make registration retries idempotent and bind registrations to the current owner/client attempt. Implement bounded registry and fair admission under the actual trusted-ingress topology. Align the documented capability grammar and failure protocol with the implementation. Formatting alone cannot certify that a caller generated entropy.

### 3.4 F03/F08 — High: prior ownership-store and raw-role failures remain reproducible

**Source:** `src-tauri/src/remote/relay_server.rs:84–108,194–254,309–405`; `src-tauri/src/remote/auth.rs:38–66,633–654`.

Two independently initialized relay instances sharing an ownership file still load separate startup snapshots. Enrolling A through one instance and B through the other leaves B in the file and loses A. This independently reproduces the shared-writer defect; it is not a claim that ordinary sequential single-instance restart protection is still absent. Whether the deployed topology uses overlapping writers is not established. Enforce an exclusive single-writer deployment or implement transactional cross-process storage rather than claiming unrestricted rollout safety.

A second probe replaces an authenticated control connection and then attaches both raw halves of a stream issued to the old owner, exchanging a frame successfully. The prerequisite is knowledge of that unpredictable issued ID. No random-ID guessing or production attack was attempted. The cleanup counter does not authenticate data/client roles or bind them to a control owner.

The identity loader also still accepts a mismatched persisted public/private pair, and the private JSON writer still ignores permission-setting failures. The malformed pair is not claimed to authenticate successfully. The control transcript still uses the constant audience `relay`, not an endpoint-specific audience. These code paths were not remediated in this generation.

**Required repair:** enforce the storage/identity invariants from the previous verdict, use separate one-use role credentials tied to machine/control generation, and invalidate old pending tickets/sessions on replacement. Retain the already working ordinary restart ownership and private first-enrollment gating.

### 3.5 F06 — Residual response-contract gap, with the header repairs explicitly credited

**Source:** `src-tauri/src/remote/relay_server.rs:791–833,958–1064`; actual gateway routes at `src-tauri/src/remote/server.rs:1728–1761`.

The new cache and Clear-Site-Data policy closes the specifically reported header problems. An independent allowed-route response confirms Cache-Control `no-store, private`, Pragma `no-cache`, the existing restrictive CSP/nosniff, and removal of all three tested origin-mutating headers. The old public-cache and Clear-Site-Data findings should not be carried forward as unchanged.

The same loopback response still forwards DELETE on an unknown `workspace/audit.js` route and accepts the synthetic daemon's **302, JavaScript MIME type and arbitrary Location**. Broad prefixes are not an exact method/path and response-type contract. No browser script was executed, no cross-host storage was read, and this report does not claim a surviving XSS exploit from this observation alone. The unresolved original contract and routing coverage remain release-assurance requirements, not proof that the specific HTML/cookie exploit still works.

The added health route now passes the allowlist. The `routes_session_when_path_is_colon_scoped` unit test only reaches a NOT_FOUND result for an offline machine; it does not validate a real gateway session endpoint. The gateway's actual sessions/devices and retained push route families are still not uniformly represented by the public proxy. Enforce the intended exact API/method/response surface, own redirect behavior at the relay, and test it against the actual gateway.

## 7. Approval gate

First remove credential-bearing candidate discovery; remain on relay until the direct endpoint is authenticated to the paired machine over a secure channel. Replace the fail-open, observation-only token cache with authoritative admission that handles restart, migration and revocation without sacrificing existing valid devices.

Complete the single daemon-owned client/coordinator/identity across GUI and CLI, exact exchange/route identity binding, safe ownership storage and generation-bound role capabilities. Enforce original registration lifetime and coherent ACK/claim/retry/reconnect semantics, public/fair resource budgets, the intended exact proxy response contract and real daemon readiness/deadlines.

Finally produce a redacted, reproducible, commit/binary-bound real browser/relay/gateway receipt covering authenticated events and grid terminal, multiple hosts, expiry, denied/revoked clients, owner replacement and restart. Keep the verified SSH, colon, response-header and short-capability fixes; do not weaken gateway authentication to make the remaining tests green.

**The review is complete. Release approval remains withheld on concrete code/security and end-to-end evidence grounds, even though successful full-suite runs now exist.**
