# Terminal pane component review (ui/src/components/TerminalPane*, NativeTerminalPane*, TerminalLinkActions*)

Scope reviewed: `ui/src/components/TerminalPane.tsx`, `ui/src/components/NativeTerminalPane.tsx`,
`ui/src/components/TerminalLinkActions.tsx`, plus the contracts they depend on
(`ui/src/components/TerminalSearchOverlay.tsx`, `ui/src/lib/nativeTerminalLifecycle.ts`,
`ui/src/state/workspaceStore.ts` reducer cases). Every citation below was opened and read.

### [P1] Input/paste/mouse callbacks capture a stale remote generation and stale outage state
- Location: ui/src/components/NativeTerminalPane.tsx:944 (also :1013 and :1140; capture sites :869, :1001, :1110)
- Observed: `sendInput` reads the live session off its closure - `const generation = isRemote ? session?.remoteGeneration ?? null : null;` (line 869) and gates on `session?.remoteConnectionState === "disconnected" || ... "reconnecting" || ... "expired"` (lines 846-850) - but the memo is declared `}, [performAttach, targetSessionId, visible]);` (line 944). `session` is not a dependency, and `performAttach` is itself stable (`}, [measureGeometry, sessionId]);`, line 812, with `measureGeometry` on `[]`, line 780). `sendPaste` (`[targetSessionId, visible]`, line 1013) and `sendMouse` (`[targetSessionId, visible]`, line 1140) have the identical defect.
- Why it is wrong: on an SSH reconnect the store updates `remoteGeneration` while `backendSessionId` stays the same (`ui/src/state/workspaceStore.ts:2149-2155` matches sessions by `session.backendSessionId !== action.status.sessionId` and then writes `remoteGeneration: action.status.generation`). Neither `targetSessionId` nor `visible` changes, so the memoized callbacks keep the pre-reconnect generation forever. Every keystroke then invokes `cmd_native_terminal_send_input` with the old `generation`, which the backend routes to `DaemonRequest::RemoteWrite { generation, .. }` (`src-tauri/src/daemon/client.rs:1262-1266`) and the host rejects as a stale generation. The user sees the "Failed to send terminal input" banner and a permanently dead keyboard in a pane whose PTY is alive. The same stale closure also defeats the outage gate in both directions: input typed during a fresh `reconnecting` state is still sent, and input typed after recovery can still be suppressed.
- Minimal fix: add the two values actually consumed to the dependency lists - hoist `const remoteGeneration = session?.remoteGeneration ?? null;` and `const remoteConnectionState = session?.remoteConnectionState ?? null;` at render scope and list them in the deps of `sendInput`, `sendPaste`, and `sendMouse` (no other restructuring needed; the effects already re-subscribe when these callbacks change).

### [P2] Input-recovery failure reports a backend-session loss without its binding key
- Location: ui/src/components/NativeTerminalPane.tsx:922
- Observed: the send-input recovery path calls `onBackendSessionUnavailable?.(currentSessionId, classification.reason);` - no third argument - whereas the attach path passes it: `onBackendSessionUnavailable?.(targetSessionId, classification.reason, bindingKey);` (line 2005). Both quarantine locally with the key (`quarantinedBindingRef.current = { sessionId: ..., bindingKey }`, lines 919 and 1994), so the key is in scope at line 922.
- Why it is wrong: the reducer's staleness guard is conditional on the key being present - `if (action.bindingKey && session.backendSessionId) { const currentBindingKey = ...` (`ui/src/state/workspaceStore.ts:2204-2206`). With `bindingKey` undefined the only remaining check is `session.backendSessionId !== action.backendSessionId`, which still matches after a daemon-epoch bump or an SSH generation bump that reuses the same backend id. A confirmed-missing verdict computed against the *old* binding therefore lands on the *new*, live binding: `SESSION_BACKEND_UNAVAILABLE` sets `lifecycle: "exited"` and `backendSessionId: null` (lines 2227-2232), the pane flips to the "Shell exited" / "SSH disconnected" overlay and the native surface is torn down, even though the PTY is still running on the host.
- Minimal fix: pass the key that is already computed and used two lines above: `onBackendSessionUnavailable?.(currentSessionId, classification.reason, bindingKey);`.

### [P2] Search overlay is handed a frontend session id when the backend id is absent
- Location: ui/src/components/TerminalPane.tsx:182
- Observed: `sessionId={session.backendSessionId ?? session.id}` is passed to `TerminalSearchOverlay`, which forwards it verbatim to the native command: `void invoke<...>("cmd_native_terminal_search", { sessionId, query: searchQuery, caseSensitive: false })` (`ui/src/components/TerminalSearchOverlay.tsx:86-90`).
- Why it is wrong: this is exactly the leafId/backendSessionId conflation that `NativeTerminalPane` documents and refuses - "When a `session` object is provided, require `backendSessionId` so we never attach with local frontend ID" (`ui/src/components/NativeTerminalPane.tsx:519-521`), implemented as `targetSessionId = isExited ? null : session ? (session.backendSessionId ?? null) : ...` (lines 525-529). When `backendSessionId` is null (exited pane, or a pane between spawn and bind - the pane still renders a retained native surface on macOS, line 536), the overlay queries the backend with a frontend pane id the native host has never seen. The rejection is swallowed by the overlay's `.catch()` (`TerminalSearchOverlay.tsx:104-110`), which sets `resultCount(0)`, so Cmd-F over visible scrollback reports "0 results" instead of failing honestly or being disabled.
- Minimal fix: pass `sessionId={session.backendSessionId}` (the overlay prop is already `sessionId?: string`, `TerminalSearchOverlay.tsx:19`, and every call site is guarded by `if (!sessionId ...)` at line 79), so a pane with no live backend binding simply performs no search.

### [P2] Terminal link routing failure is silently swallowed after the toast is dismissed
- Location: ui/src/components/TerminalLinkActions.tsx:32
- Observed: the action handler dismisses the prompt first, then discards any failure - `toast.dismiss(t); try { await routeHttpLink(url, { source: "terminal", destination }); ... } catch { // ignore routing error }` (lines 22-34).
- Why it is wrong: the user clicks "Built-in Browser" or "Web Browser" on a terminal link; the prompt disappears, nothing opens, and no error surfaces. Because the toast was created with `{ duration: Infinity }` (line 93) it is the only UI affordance for that link, and it is already gone - the URL cannot be retried without reproducing the terminal output. The remembered-choice persistence (`saveBrowserSettings`, lines 27-30) is correctly inside the try, so a failed route also silently drops the preference the user just checked.
- Minimal fix: replace the empty catch with a user-visible failure, e.g. `} catch (error) { toast.error(\`Failed to open ${url}\`); }`, keeping the rest of the handler unchanged.

### [P3] Native paste/copy fallback picks an arbitrary pane from Map insertion order
- Location: ui/src/components/NativeTerminalPane.tsx:1530 (same pattern at :1569 and :1325/:1460)
- Observed: `const fallbackSessionId = lastFocusedNativeTerminalSessionId ?? mountedNativeTerminalSessionCounts.keys().next().value;` followed by `if (fallbackSessionId !== targetSessionId) return;`. `lastFocusedNativeTerminalSessionId` is reset to `null` whenever the last mount of the focused session unmounts (lines 1306-1309).
- Why it is wrong: with several split panes mounted and no focus record (right after the focused pane is closed, or right after an HMR/StrictMode remount cycle), the "first key in the Map" is whichever pane happened to register first, not the one under the cursor. A native paste or copy/interrupt then targets that pane. It is not a corruption path - the pane still owns a live PTY and the DOM checks above filter out editable focus - but the routing is order-dependent rather than intent-dependent.
- Minimal fix: when `lastFocusedNativeTerminalSessionId` is null, resolve the fallback from the hovered pane element already queried for keyboard ownership (`document.querySelector('.terminal-host[data-native-terminal-visible="true"]:hover')`, lines 1320-1322) and bail out when neither is available, instead of taking `keys().next().value`.

## Notes on paths checked and found sound
- The pane-drag / HMR teardown path is guarded: the surface effect's cleanup (`ui/src/components/NativeTerminalPane.tsx:2077-2135`) only detaches after checking the retained-presentation handoff (lines 2102-2109), and `attachNativeTerminalLifecycle` cancels a queued detachment for the same backend id synchronously before the detach microtask fires (`ui/src/lib/nativeTerminalLifecycle.ts:195-212, 310-315`). No confirmed path where a re-render or HMR replay destroys a live PTY.
- `cmd_native_terminal_detach` only drops the compositor host and layout (`src-tauri/src/native_terminal/surface_host.rs:1944-1962`); the PTY-destroying command is `cmd_native_terminal_close`, which these components never invoke.
- Every `window`/`document` listener registered in these components has a matching removal in its cleanup (lines 746-747, 1263-1265, 1287-1289, 1512-1515, 2077-2078), as does the link-action listener (`TerminalLinkActions.tsx:97-98`); the `onNativeTerminal*` Tauri subscriptions all use the `disposed` + `unlisten` pattern that disposes a listener resolving after teardown.
