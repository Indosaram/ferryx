### [P1] macOS notarization is skipped by default and nothing downstream notices
- Location: `scripts/lib/release-platforms.mjs:724`, `scripts/lib/release-platforms.mjs:1004`
- Observed: `buildHost` defaults the flag off — `  approveNotarization = false,` (line 724) — and the entire notarization stage is gated on it: `      if (approveNotarization && hostConfig.notaryProfile) {` (line 1004). Everything inside that block is skipped when the flag is absent: `xcrun notarytool submit` (1011), `xcrun stapler staple/validate` (1016-1017, 1028-1029), and — decisively — the only Gatekeeper gate in the whole file, `const spctlApp = spawnSync("spctl", ["-a", "-vvv", "-t", "install", appPath], ...)` (1033) with its `Notarized Developer ID` assertion (1035). The build then proceeds straight to `// 5. Create updater tar from verified (and stapled) .app` (1048) and tars the un-notarized bundle into `Ferryx.app.tar.gz`. The same default also strips Tauri's own notarization credentials from the build env (`delete buildEnv.APPLE_API_KEY;` … `delete buildEnv.APPLE_PASSWORD;`, 863-867), so the bundler cannot notarize either. The receipt schema (`scripts/lib/release-contract.mjs:95-108`: `kind`, `name`, `relPath`, `bytes`, `sha256`, `signatureRelPath`, `targets`) carries no notarization field, so `assembleRelease` in `scripts/build-latest-json.mjs` has nothing to check and publishes the artifact.
- Why it is wrong: a release built with the default invocation exits 0, produces a receipt that validates, and ships a DMG and an updater tarball that macOS Gatekeeper refuses: users double-clicking the DMG get "Apple could not verify Ferryx is free of malware" and cannot open the app. Nothing in the pipeline — not the build, not the receipt, not `build-latest-json.mjs` — reports that the step was skipped. The one check that would have caught it (`spctl`, line 1033) is inside the branch that was skipped, which is the definition of a silently skippable gate.
- Minimal fix: move the Gatekeeper assertion out of the conditional — after the `if (approveNotarization …)` block, unconditionally run `spctl -a -t install` on `appPath` (and `dmgPath`) and throw unless the output contains `Notarized Developer ID`. Then `--approve-notarization` controls *how* notarization happens, not *whether* the release is allowed to ship un-notarized.

### [P1] macOS codesigning is entirely optional: omit one config key and every codesign step disappears
- Location: `scripts/lib/release-platforms.mjs:859`, `scripts/lib/release-hosts.mjs:244`
- Observed: `signingIdentity` is an optional host field — `    if (host.signingIdentity !== undefined) {` (release-hosts.mjs:244) validates it only when present, and line 263 emits it only when defined. Every signing action in the macOS build is then guarded by `      if (hostConfig.signingIdentity) {`: env injection (859), hardened-runtime pre-signing of the universal binaries (899-907), re-signing of `Contents/MacOS/*` and the app bundle (960-975), the "signed with expected identity" assertion (980-989), and DMG signing (1020-1022). The preflight probe is guarded the same way (`    if (hostConfig.signingIdentity) {`, line 108) and simply reports `hasSigningIdentity: false` (line 26) without failing.
- Why it is wrong: a `release-hosts.json` that is missing (or has a typo in) `signingIdentity` produces a full release run that never signs anything and never errors — the identity-verification assertion at line 985 is itself inside the skipped branch. The operator gets artifacts that look complete and pass receipt validation, and the failure surfaces only on an end user's machine.
- Minimal fix: in `buildHost`, for `hostName === "macbook"`, throw before the build if `hostConfig.signingIdentity` is unset (or require the operator to pass an explicit `--allow-unsigned` opt-out), so the absence of a signing identity is a hard error rather than a silent no-op.

### [P1] The hosted-release policy guard fails open on multi-line run steps
- Location: `scripts/release-workflow-policy.mjs:55`
- Observed: the root-build rule (line 126) rejects `bun run build` in a workflow step unless `isScopedFrontendBuild` says otherwise, and that helper tests the *entire* run block as one string: `  if (/--cwd\s+(?:ui|site)\b/.test(runCmd)) return true;` (line 55). A single `run:` block such as `bun install --cwd ui --frozen-lockfile` followed on the next line by `bun run build` is therefore classified as a scoped frontend build. I confirmed this by evaluating both regexes against that exact two-line string: the forbidden-build pattern matches (`true`) and `isScopedFrontendBuild` also returns `true`, so the violation is suppressed. `package.json:7` defines `"build": "cargo tauri build"`, i.e. the suppressed command is the full Tauri release bundle. The `working-directory` fallbacks (lines 57-59) use unanchored `/(?:ui|site)/`, so any directory whose name merely contains `ui` or `site` (`suite`, `website`, `build-ui-x`) also whitelists a root build.
- Why it is wrong: this is the source-enforced local-release boundary. A hosted workflow can reintroduce a full `cargo tauri build` release producer — the thing this file exists to prevent — and `bun scripts/release-workflow-policy.mjs` still prints `PASS` (I ran it against the live `.github/workflows`: exit 0, "All evaluated workflows comply"). The guard gives false assurance precisely in the shape a real workflow is written (install + build in one `run: |` block).
- Minimal fix: split `step.run` on newlines and evaluate each command line independently, passing only that line to `isScopedFrontendBuild`; anchor the working-directory checks with `/^(?:ui|site)(?:\/|$)/` instead of a bare substring match.

### [P1] `build-msix.ps1` packages without icons on a warning while hard-failing on every other resource
- Location: `scripts/build-msix.ps1:329`
- Observed: required resources are hard gates — `            throw "ERROR: Required MSIX resource missing: $required"` for `ui/dist/index.html` and the helper manifest (line 294), plus length/SHA256 verification of every helper binary (line 285). Icons are not: when no icon directory resolves, the script only warns and continues — `        Write-Warning "Icon folder not found. MakeAppx may fail if icons are missing."` (line 329) — and then packs with semantic validation disabled: `    & $makeAppx pack /d $stagingDir /p $msixOutputFile /nv /o` (line 370, `/nv` = skip validation). The post-pack check `Validate-PackagedManifest` (line 380) inspects only `<Identity>` Name/Version/Publisher/ProcessorArchitecture (lines 421-436) and never looks at `Assets\`. The manifest template references ten assets (`src-tauri/windows/msix/AppxManifest.xml:17,37-49`: `Assets\StoreLogo.png`, `Square150x150Logo.png`, `Square44x44Logo.png`, `Square310x310Logo.png`, …).
- Why it is wrong: with `/nv` there is no missing-asset check anywhere in the pipeline, so the script can emit a "BUILD SUCCESSFUL" MSIX whose manifest points at logo files that are not in the package. That package is then picked up unconditionally by the remote build script (`scripts/lib/release-platforms.mjs:674-676`, `Expected exactly one non-empty MSIX`) and published — the operator discovers it only via Store certification rejection or blank tiles on a user's Start menu. The author's own warning text ("MakeAppx *may* fail") concedes the step is not enforced.
- Minimal fix: after resolving `$iconSource`, assert that each `Assets\*.png` referenced by the manifest template exists in `$stagingDir\Assets` and `throw` otherwise — matching the hard failure already used for `ui/dist` and the helper binaries 30 lines above.

### [P1] Release MSIX is always built unsigned, and the published asset is a sideload-named file nobody can install
- Location: `scripts/lib/release-platforms.mjs:671`
- Observed: the Windows remote build always requests the unsigned path: `& (Join-Path $sourceDir 'scripts/build-msix.ps1') -ExePath $executables[0].FullName -Version … -OutputDir $outDir -SkipSigning` (line 671). In `build-msix.ps1`, `-SkipSigning` prints `Store packaging mode (-SkipSigning): package created unsigned for Microsoft Store ingestion.` (line 232) and the whole SignTool stage (lines 451-458) is skipped. The artifact contract publishes it under a sideload-style stable alias — `scripts/lib/release-contract.mjs:62-67`: `msix: { … stableAlias: "Ferryx_x64.msix", allowedExtensions: [".msix"] }` with `isUpdater: false` — and the remote script renames to exactly that name (`scripts/lib/release-platforms.mjs:676`). `build-latest-json.mjs` stages the alias for publication (`stageFile(alias, fullPath, artifact.sha256)`), and because `isUpdater` is false no signature is ever required for it.
- Why it is wrong: `Ferryx_x64.msix` appears on the GitHub release page next to the signed/notarized macOS and NSIS assets, but Windows refuses to install an unsigned MSIX by double-click — the user gets "This app package is not signed with a trusted certificate". There is no other code path in the repo that ever signs this file, so the "Store ingestion" justification never materializes for anyone downloading the release.
- Minimal fix: either stop publishing the MSIX as a release asset (drop the `msix` kind from `requiredKinds`, keep it as a Store-submission-only local output), or pass `-CertThumbprint` from host config on the release path so the published `.msix` is sideload-signed.

### [P2] Explicit `-IconsDir` / `-ManifestTemplate` paths are silently ignored when they do not exist
- Location: `scripts/build-msix.ps1:309`, `scripts/build-msix.ps1:334`
- Observed: `    if ($IconsDir -and (Test-Path $IconsDir)) {` (309) and `    if ($ManifestTemplate -and (Test-Path $ManifestTemplate)) {` (334). When the operator passes a path that does not exist, the condition is false and control falls into the repo-relative candidate search (`$candidates = @(…); foreach ($c in $candidates) { if (Test-Path $c) { $templateSource = $c; break } }`, 337-343).
- Why it is wrong: a typo in `-ManifestTemplate` does not fail; it silently substitutes `src-tauri/windows/msix/AppxManifest.xml`, so the operator ships a package built from a different manifest than the one they named, with a "BUILD SUCCESSFUL" banner. The same applies to `-IconsDir`, which then falls through to the warning path in the finding above. (When no candidate matches either, the error message is also degenerate: `throw "ERROR: Manifest template not found at $templateSource"` interpolates an empty `$templateSource`.)
- Minimal fix: when the parameter is non-empty, `throw` if `Test-Path` fails instead of falling through — `if ($ManifestTemplate) { if (-not (Test-Path $ManifestTemplate)) { throw "ERROR: -ManifestTemplate not found: $ManifestTemplate" }; $templateSource = $ManifestTemplate }`, and likewise for `-IconsDir`.

### [P2] `2>&1` plus `$ErrorActionPreference = "Stop"` makes the MSIX test suite report results from stderr, not exit codes
- Location: `scripts/test-build-msix.ps1:6`, `scripts/test-build-msix.ps1:219`
- Observed: the suite sets `$ErrorActionPreference = "Stop"` (line 6) and then runs every child build with merged streams, e.g. the success-path test `            $procOutput = & powershell.exe -NoProfile -NonInteractive -Command "& '$buildMsixScript' …-SkipSigning" 2>&1` immediately followed by `            if ($LASTEXITCODE -ne 0) {` (lines 219-220); the same `2>&1` pattern appears in the negative tests at 134, 147, 161, 175, 189, 262, 276, 301, 488, 540.
- Why it is wrong: under Windows PowerShell 5.1 — the host that `powershell.exe` itself denotes, and a normal way to run this suite — redirecting a native command's stderr with `2>&1` while `$ErrorActionPreference` is `Stop` turns the first stderr line into a terminating `NativeCommandError`. The child emits stderr on ordinary paths (`Write-Warning "Icon folder not found…"`, build-msix.ps1:329, plus any MakeAppx diagnostics), so the `if ($LASTEXITCODE …)` assertion on the very next line never executes and `Run-Test`'s catch records a FAIL whose message is the child's stderr rather than the assertion. Test outcomes then depend on whether the child happened to write to stderr instead of on what it returned — the suite grades the wrong signal.
- Minimal fix: scope the preference around the child invocations — wrap each `& powershell.exe … 2>&1` in `$ErrorActionPreference = 'Continue'` (restoring afterwards), or capture with `-RedirectStandardError` via `Start-Process` — so the exit-code assertions on the following lines are the only thing that decides pass/fail.
