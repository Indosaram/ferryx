# Ferryx 워크트리 디스크 관리 — 구현 범위 확정서

**작성:** 2026-09-12 · **상태:** 범위 확정, 착수 대기 · **실행표 ②번**

워크트리를 여러 개 파서 에이전트를 돌리면 `.orca-worktrees/` 아래에 체크아웃과 빌드 산출물이 계속 쌓이는데, 지금은 **무엇이 얼마나 먹고 있는지 앱 안에서 볼 방법이 전혀 없다.** 사용자는 디스크가 찰 때까지 모른다.

---

## 1. 확정된 결정

- **독립 기능으로 분리한다.** 사이드바 워크트리 목록 진입 경로에는 스캔을 일절 붙이지 않는다. 용량 측정은 사용자가 "워크트리 디스크 관리" 화면을 열었을 때만 도는 **온디맨드 작업**이다. 일상 UI가 무거운 디렉터리 순회에 결코 묶이지 않게 하는 것이 이 결정의 목적이다.
- **표시는 별도 관리 다이얼로그.** 사이드바 행은 그대로 두고, 관리 화면에서 용량·마지막 사용·상태를 정렬 가능한 목록으로 보여주고 거기서 정리한다.
- **정리 후보 기준 = `git prunable` + N일 미사용(기본 14일).** *(사용자 미응답 → 작성자 결정)* prunable은 이미 `Worktree` 타입에 실려 오므로 추가 비용이 0이고, 마지막 사용은 `git for-each-ref`의 committerdate로 얻는다(`ipc/project.rs:263`에 동일 패턴 존재). **병합된 브랜치 판정은 2차로 미룬다** — 기준 브랜치가 `main`/`master`/`origin/HEAD` 중 무엇인지 저장소마다 달라 오판 시 살아 있는 작업을 정리 후보로 올리는 사고가 난다.
- **삭제는 경고 후 진행.** 더티 워크트리도 무엇을 잃는지 명시하고 확인받아 진행한다. 차단하지 않는다.

## 2. 이미 있는 것 (재사용)

- **커맨드 6종 완비** — `cmd_worktree_list` / `_create` / `_delete` / `_delete_destructive` / `_delete_preview` / `_status` (`src-tauri/src/ipc/worktree.rs`).
- **더티 판정 완비** — `worktree/model.rs:65` `is_dirty`, `DirtyFile` 목록. 기본 삭제 경로는 더티를 **거부**하고(`"dirty (N uncommitted/untracked files); deletion forbidden for 1-writer-1-worktree isolation"`), 별도의 destructive 경로가 존재한다. 즉 "경고 후 진행"은 신규 배선이 아니라 **`_delete_preview` → 확인 → `_delete_destructive`** 조립이다.
- **확인 다이얼로그** — `ui/src/components/WorktreeDeleteDialog.tsx` 존재. 관리 화면의 삭제 확인에 재사용한다.
- **git 신호** — `Worktree.prunable`, `Worktree.locked`가 이미 프론트까지 온다.
- **git 메타 조회 패턴** — `for-each-ref` 사용 선례가 `ipc/project.rs:263`에 있다.

## 3. 없는 것 (실제 신규 작업)

디스크 용량 계산이 **0건**이다(`size|du|bytes|disk` 검색 무결과). 마지막 사용 시각, 관리 화면, 정리 후보 배지도 없다.

## 4. 기술 제약

- **`du` 금지.** 크로스플랫폼 전제(macOS/Windows/Linux)이므로 유닉스 전용 외부 명령에 의존할 수 없다. `std::fs` 재귀 순회를 직접 작성하거나 순회 크레이트를 추가해야 한다 — 현재 `walkdir`/`ignore`/`jwalk` **모두 미의존**이다.
- **`run_blocking` 필수.** 수십만 파일 순회는 동기 디스크 I/O이므로 Tokio 런타임 스레드에서 돌리면 안 된다(AGENTS.md 금지 사항).
- **취소 가능해야 한다.** 대형 저장소 스캔은 수십 초가 걸릴 수 있으므로 다이얼로그를 닫으면 중단되어야 하고, 진행률을 보여줘야 한다.
- **수치는 근사치다.** 파일 크기 합(apparent size)은 macOS APFS 클론이나 하드링크를 중복 계산할 수 있어 "삭제하면 실제로 회수되는 양"과 다를 수 있다. UI 문구가 이를 단정하지 않아야 한다.

## 5. 작업 분해

- **A. 용량 스캐너(Rust)** — 경로별 재귀 크기 합산, `run_blocking` 위에서 실행, 취소 토큰 + 진행률 이벤트.
- **B. 메타 수집** — 워크트리별 마지막 커밋 시각(`for-each-ref`), `prunable`/`locked`/`is_dirty` 취합. 스캔 결과와 병합한 단일 DTO.
- **C. Tauri 커맨드** — 스캔 시작/취소/결과 조회. 결과는 세션 내 캐시하고 명시적 새로고침으로만 갱신.
- **D. 관리 다이얼로그(UI)** — 용량 내림차순 정렬 목록, 정리 후보 배지(prunable / N일 미사용), 진행률, 빈 상태, 스캔 실패 표시.
- **E. 정리 플로** — 선택 → `_delete_preview`로 잃는 것 제시 → 확인 → 클린이면 `_delete`, 더티면 `_delete_destructive`. `WorktreeDeleteDialog` 재사용.
- **F. 테스트** — 스캔 취소, 심링크 순환 방지, 더티 워크트리 경고 경로, prunable 배지 판정, 삭제 후 목록 갱신.

## 6. 위험

- **스캔 비용이 사용자 기대를 넘길 수 있다.** `node_modules`·`target`이 있는 워크트리 여러 개면 첫 스캔이 길다. 진행률과 취소가 없으면 멈춘 것처럼 보인다(D·A에 포함).
- **정리 후보 오판.** N일 미사용은 "마지막 커밋"이지 "마지막 작업"이 아니다. 커밋 없이 오래 실험 중인 워크트리가 후보로 뜰 수 있으므로 배지는 권고일 뿐 자동 선택이 되어서는 안 된다.
- **경고 후 진행은 되돌릴 수 없다.** 더티 삭제는 커밋되지 않은 작업을 영구 삭제한다. 프리뷰가 파일 목록과 개수를 반드시 보여줘야 한다.

## 7. 범위 밖

병합 브랜치 기반 후보 판정(2차), 자동 정리·스케줄러, 저장소 전역 GC(`git gc`), 빌드 산출물 선별 삭제(`target/`만 지우기 등).
