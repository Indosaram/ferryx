# SSH 원격 플랫폼 지원 설계 제안

작성일: 2026-09-08
상태: 제안. 구현 및 실환경 검증 전.

후속 구현과 검증 결과: [SSH_REMOTE_PLATFORM_IMPLEMENTATION.md](SSH_REMOTE_PLATFORM_IMPLEMENTATION.md).
아래는 구현 승인 당시의 설계 제안이며, 실제 전송 방식과 검증 범위는 후속 문서를 따른다.

## 결론

시스템 OpenSSH 전송은 유지하고, 원격 실행 환경을 확인한 뒤 POSIX 또는
Windows 실행기로 모든 원격 작업을 보내는 경계를 만든다. `true` 교체,
Windows SSH 기본 셸 변경, WSL 강제 전환만으로 완료 처리하지 않는다.
원격 상주 데몬이나 Python/Node 설치를 필수 조건으로 추가하지 않는다.

## 확인한 근거

- 사용자 오류는 원격 PowerShell이 `true`를 실행하다 발생시킨
  `CommandNotFoundException`이다. SSH 인증 이전 실패와 구분해야 한다.
- `src-tauri/src/ipc/ssh.rs`의 `cmd_ssh_test_connection`은 `true`를 실행하고,
  성공하면 원격 확장을 백그라운드 설치한다. 테스트와 설치가 결합되어 있다.
- `src-tauri/src/ssh/direct.rs`는 경로를 POSIX 절대 경로로 제한한다.
  터미널은 `export`, `exec`, `/bin/sh`, 상태 전달은 `/tmp/*.sock`,
  업로드는 `cat`, `chmod`, `find`, 확장 설치는 `sh`에 의존한다.
- 같은 파일의 `collect_output`은 비정상 종료를 `InvalidPath`와
  `SSH validation failed`로 합치고 stderr를 UTF-8로 손실 변환한다.
- `src-tauri/src/ipc/project_remote.rs`는 호스트 조회 전에 POSIX 경로 검증을
  수행한다. 등록 성공 후에도 원격 확장을 자동 설치한다.
- `src-tauri/src/ssh/projects.rs`의 프로젝트 ID는 호스트 ID와 경로 문자열의
  해시다. `resolve` 역시 POSIX 경로 검증을 호출한다.
- `src-tauri/src/ssh/worktree.rs`에는 명령 문자열 생성기가 있다. 실제 제품
  호출 경로와 현재 지원 연산은 구현 착수 시 확인해야 하며, 생성기 존재만으로
  원격 워크트리 기능이 완성되어 있다고 간주하지 않는다.
- 읽은 실제 SSH/PTY 테스트는 Unix loopback과 `printf`, `pwd -P` 중심이다.
  이 테스트 통과는 Windows 원격 지원의 증거가 아니다.

## 실행 구조

### 공통 전송과 원격 실행을 분리

OpenSSH 전송부는 호스트 옵션, 인증, 호스트 키 확인, 프로세스 수명,
타임아웃, stdout/stderr 바이트 수집만 담당한다.
기존 포트, 키, 점프 호스트 및 신뢰 정책을 모든 작업에 동일하게 적용한다.

작업 호출자는 셸 문자열 대신 명시적 작업과 데이터를 전달한다.
최초 분리는 환경 탐지, 디렉터리 확인, 터미널 시작, Git 실행, 임시 파일
업로드, 확장 준비 정도로 제한한다. 두 실행기를 위한 enum과 모듈로 시작하며,
플러그인 프레임워크나 범용 원격 RPC 시스템은 만들지 않는다.

### 원격 환경을 실행 결과로 확인

호스트 이름, 로컬 OS, SSH 배너만으로 원격 OS를 추측하지 않는다.
연결 정보와 별도로 원격 OS, 검증된 실행기, 실행기 버전, 경로 방식,
홈/임시 디렉터리, Git 및 상태 전달 기능을 기록한다.

최초 탐지는 읽기 전용이며 한 번의 전체 시간 예산 안에서 수행한다.
지원 셸에서 가능한 ASCII 응답으로 명령 채널을 확인하고, 명시적인
PowerShell 및 POSIX 실행기 탐지에서 버전이 있는 구조화 응답을 검증한다.
`pwsh`가 설치되어 있다는 이유만으로 Windows라고 판단하지 않는다.
알 수 없는 환경은 명확하게 미지원으로 남긴다.

OpenSSH 종료 코드 255만으로 인증, DNS, 호스트 키 오류를 정확히 분리했다고
주장하지 않는다. 확실한 단계와 원문 진단을 보존하며, 판별 근거가 없으면
일반 SSH 오류로 보고한다. 지역화된 오류 문장을 정규식으로 분류하지 않는다.

탐지 결과는 연결 설정 변경 시 무효화하고 새 연결에서 재확인한다.
탐지 도중 호스트 설정이 바뀌면 결과를 저장하지 않는다.
기존 호스트에는 최초 사용 시 탐지를 적용한다.

### Windows와 POSIX 실행 규약

- POSIX: 자동화 작업은 명시적인 `sh` 실행 경계로 보낸다.
  기본 로그인 셸이 fish/zsh여도 POSIX 스크립트를 그 셸이 직접 해석하지 않게 한다.
- Windows: 기본 셸이 cmd 또는 PowerShell이어도 자동화 작업은 검증된
  `powershell.exe` 또는 `pwsh`를 명시적으로 실행한다.
  Windows PowerShell 5.1과 PowerShell 7을 각각 검증 대상으로 둔다.
- PowerShell 부트스트랩은 `-NoProfile -NonInteractive -EncodedCommand`와
  UTF-16LE 인코딩을 사용한다. 사용자 경로를 부트스트랩 셸 문법에 직접 삽입하지
  않고 데이터로 전달한다. POSIX 인용과 PowerShell 인용은 섞지 않는다.
- 응답은 버전/요청 식별자가 있는 프레임 안에 UTF-8 데이터로 반환한다.
  POSIX에 JSON 도구 설치를 요구하지 않는다. 작고 고정된 응답은 NUL 구분
  UTF-8 필드 등으로 구현할 수 있다. 프레임 밖 배너는 진단으로만 취급한다.
- PowerShell의 예외뿐 아니라 네이티브 Git의 종료 코드도 검사한다.
  PowerShell 파이프라인 성공 여부로 Git 성공을 대신하지 않는다.
- 자동화 데이터 채널과 대화형 PTY는 별도다. PTY에는 사용자 셸, 현재 디렉터리,
  환경 변수, 입력 및 크기 변경을 보존하는 전용 시작 경로를 둔다.

## 경로, 프로젝트 식별자 및 WSL

로컬 `PathBuf::canonicalize`로 원격 경로를 판단하지 않는다.
원격 실행기가 실제 파일시스템에서 경로를 확인하고 안정적인 표기를 반환한다.
Windows 드라이브 절대 경로와 POSIX 절대 경로를 구분하고 상대 드라이브 경로
`C:repo`는 절대 경로로 취급하지 않는다. UNC는 해당 연산의 접근성과 Git 지원을
확인한 경우만 허용한다. 문자열 전체 소문자화로 Windows 경로를 합치지 않는다.
워크트리 루트 제한은 원격 정규 경로와 구성 요소 단위로 확인한다.

Windows OpenSSH와 WSL Linux SSH는 다른 실행 환경이다.
현재 `maho-win`은 Windows 자체를 지원하는 대상이며 WSL로 자동 우회하지 않는다.
WSL 자체 SSH 엔드포인트는 Linux 환경으로 취급한다. 같은 Windows 엔드포인트를
통한 `wsl.exe -d ...` 모드는 별도 기능이며, 추가할 경우 배포판까지 프로젝트
식별자에 포함해야 한다.

기존 POSIX 프로젝트 ID와 레이아웃 참조는 유지한다. 새로운 환경 정보가
누락된 레코드는 재탐지하되 기존 ID를 조용히 재해시하지 않는다.
기존 호스트의 실행 환경이 바뀌면 같은 경로 문자열을 다른 환경에 연결하지 말고
재등록을 요구한다. 명시적 WSL 모드 도입 시에는 버전 있는 ID 전환이 필요하다.

## 나머지 기능도 같은 실행 경계를 사용

- 프로젝트 등록과 Git: 원격 경로 확인, Git 루트/원격 URL 조회 및 현재 제품에
  노출된 워크트리 연산을 같은 실행기로 보낸다. Git 출력의 인용/인코딩과
  공백·한글·특수문자 경로를 실제 Git 프로세스로 확인한다.
- 이미지 업로드: PTY 없이 stdin 원시 바이트를 전송한다.
  Windows에서는 .NET 바이트 스트림을 사용하며 PowerShell 텍스트 파이프라인을
  거치지 않는다. 임시 위치와 정리는 OS별로 처리하고 업로드 전후 해시를 검증한다.
  사용자 간 접근 제한은 Windows ACL과 POSIX 권한 각각으로 검증한다.
- 에이전트 상태: Unix 소켓 역방향 포워딩을 Windows의 기본 기능으로 가정하지
  않는다. 기존 수신부와 확장 프로토콜을 확인한 뒤 Windows용 루프백 TCP 전달을
  추가하고 SSH 터널 안에서만 운용한다. 세션별 인증과 수명 관리를 포함한다.
  해당 기능이 없거나 터널이 실패해도 터미널 연결 자체를 실패로 오인하지 않는다.
- 확장 준비: Test와 프로젝트 읽기 검증에서 자동 설치를 제거한다.
  별도 설정/준비 동작에서 수행하고 결과를 숨기지 않는다.
  원격 코딩 에이전트 설치는 여전히 필수 전제가 아니다.

## 사용자에게 보여줄 상태

한 개의 `reachable` 값으로 모든 결과를 표현하지 않는다.
연결 진단 단계와 기능 상태를 분리해 다음 사실을 각각 전달한다.

- SSH 명령 채널 확인 여부.
- 원격 환경과 사용 가능한 실행기.
- 디렉터리 접근 및 Git 사용 가능 여부.
- 선택적인 에이전트 상태 연동 준비 여부.

오류는 단계, 기계 판독 코드, 종료 코드, 원문 진단을 보존한다.
Ferryx가 생성하는 응답은 명시적 UTF-8로 통일하지만 OpenSSH 자체 진단까지
항상 UTF-8이라고 가정하지 않는다. 알 수 없는 인코딩은 원시 바이트를 보존하고
판별 한계를 표시한다. 모든 실패를 경로 오류로 매핑하지 않는다.

## 구현 순서와 완료 기준

1. 현재 실패를 실제 Windows PowerShell SSH 테스트로 고정한다.
   전송 결과와 환경 탐지를 분리하고 Test의 원격 쓰기 부작용을 제거한다.
2. 환경별 경로 확인과 프로젝트 등록을 적용한다. 기존 POSIX 프로젝트 및
   저장된 레이아웃 ID가 그대로 복원되는지 확인한다.
3. Windows/ POSIX 터미널 시작을 연결해 신규 탭, 분할, GUI 재연결에서
   실제 원격 현재 디렉터리와 입력/출력을 검증한다.
4. 제품에 노출된 Git/워크트리 작업과 바이너리 업로드를 같은 경계로 이관한다.
5. 선택적 확장 준비와 Windows 상태 전달을 연결하고 진단 상태를 UI에 노출한다.

완료는 Test 버튼이 초록색이 되는 시점이 아니다. 다음 증거가 필요하다.

- 실제 maho-win Windows OpenSSH: PowerShell 기본 셸 재현 및 해결.
  cmd 기본 셸 조건은 별도 격리 환경에서 확인하며 사용자 호스트 설정을 바꾸지 않는다.
- Windows PowerShell 5.1/PowerShell 7, Linux, macOS 원격 셸을 각각 실행한다.
  WSL 자체 SSH도 Linux 회귀 대상에 포함한다.
- 공백, 한글, 작은따옴표, `$`, `&`, 괄호가 있는 허용 경로에서 실제 경로와
  실행 결과가 일치한다. 특수문자가 다른 명령으로 실행되지 않는다.
- 실제 SSH/PTY에서 입력 에코와 구분되는 응답, 현재 디렉터리, 크기 변경,
  신규 탭/분할, GUI 재연결 후 살아 있는 세션을 확인한다.
- 임시 테스트 저장소에서 노출된 Git 연산을 실행하고 바이너리 업로드 해시를 비교한다.
  테스트 소유 자원만 정리하며 기존 사용자 세션이나 데몬을 종료하지 않는다.
- 인증/호스트 키 실패, 미지원 실행기, Git 없음, 경로 없음, 시간 초과,
  깨진 응답 및 상태 터널 실패가 해당 단계로 보고된다.
- async 테스트는 이벤트를 먼저 구독한 뒤 동작을 시작하며 고정 sleep으로 통과하지 않는다.
- 데스크톱 검증은 `bun tauri dev` 디버그 앱만 사용한다. 사용자 데스크톱을
  자동 조작하지 않으며 Settings와 실제 터미널의 수동 확인을 사용자에게 요청한다.

## 이번 제안의 검증 범위

사용자 오류 및 위 소스를 읽어 설계했다. 원격 명령 실행, 빌드, 테스트,
앱 변경은 하지 않았다. 독립 설계 검토는 모델 크레딧과 인증 오류로 실행되지
못했으므로 외부 검토 완료를 주장하지 않는다. 이 문서는 구현 승인을 위한 제안이며
실행기 탐지와 명령 인코딩의 실환경 성공을 아직 증명한 문서가 아니다.
