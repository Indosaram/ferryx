I read this as a read-only UI/UX audit - below is the complete prioritized review with verified `ui/src/` citations and suggested fixes.

# Ferryx UI/UX and Styling Review

## Executive summary

The UI has a solid technical foundation:

- A coherent semantic color-token layer backed by Tailwind.
- Recursive tab-group and terminal-pane layouts.
- Typed drag/drop payloads and command resolution.
- Shared primitives for icon buttons and activity status.
- Good native browser-webview cleanup and bounds synchronization.
- Correct Ferryx naming in visible product copy and the active application icon.

No **Critical** issue was found. The most important **Warnings** are:

1. Browser Back/Forward controls can become enabled while having no callback.
2. Pane-center swapping is effectively shadowed by the group-body drop target.
3. Modal surfaces lack complete focus trapping and focus restoration.
4. Tab, context-menu, and splitter keyboard behavior is incomplete.
5. Hidden pane controls remain in the keyboard focus order.
6. Mobile key-dock controls lack accessible names/state and have a modifier-latching bug.
7. Density settings do not affect most of the interface because typography is primarily fixed in pixels.
8. A legacy `orca-logo.svg` remains in shipped source assets, while the Ferryx icon test only checks existence.

# 1. Component Architecture & Hierarchy

## Current hierarchy

The principal hierarchy is:

```text
TerminalSplitView
└── DndContext
    └── TabGroupLayoutRenderer (recursive group split tree)
        ├── TabGroupView
        │   ├── TabBar
        │   │   ├── SortableContext
        │   │   │   └── SortableTab[]
        │   │   ├── NewTabPopover
        │   │   └── TabContextMenuPopup
        │   └── TabGroupDropSurface
        │       ├── BrowserPane
        │       │   └── BrowserToolbar
        │       └── PaneRenderer (recursive terminal split tree)
        │           ├── PaneLeafView
        │           │   ├── PaneEdgeDropZones
        │           │   ├── hover pane toolbar / drag handle
        │           │   └── TerminalPane
        │           └── PaneResizeDivider
        └── PaneResizeDivider for tab groups
```

This separation between whole-tab groups and terminal panes is conceptually strong. Whole-tab splitting is handled by `TabGroupLayoutRenderer`, while terminal-local splitting is handled by `PaneRenderer` and `PaneLeafView` (`ui/src/components/TerminalSplitView.tsx:447-490`, `730-775`, `793-910`).

`TabBar` also correctly keeps the add-button/popover wrapper outside the horizontal tab overflow container, avoiding vertical clipping by the scroll viewport (`ui/src/components/TabBar.tsx:165-200`).

## Architectural findings

### Warning — `TerminalSplitView` combines too many responsibilities

`TerminalSplitView.tsx` is 995 lines and owns:

- Collision detection.
- Drag snapshot/focus state.
- Drop-command execution.
- Recursive group layout.
- Recursive pane layout.
- Browser/terminal selection.
- Pane toolbar behavior.
- Resize behavior.

The orchestration begins around `ui/src/components/TerminalSplitView.tsx:140`, drop execution occupies `249-330`, group rendering begins at `447`, pane rendering at `730`, and resizer handling at `921`.

This makes changes to DnD mechanics likely to affect rendering and focus behavior unintentionally.

**Suggested solution**

Separate without changing the underlying data model:

- `useWorkspaceDragDrop()` for sensors, collision detection, snapshots, and drop execution.
- `TabGroupLayoutRenderer.tsx`.
- `PaneRenderer.tsx`.
- `PaneResizeDivider.tsx`.
- Keep `TerminalSplitView` as the composition boundary.

This is a maintainability recommendation, not a request for a wholesale pane-state refactor.

### Warning — modal/dialog behavior is duplicated rather than shared

`CommandPalette`, `ProjectDialogs`, `WorktreeDeleteDialog`, `NewTabPopover`, and `TerminalLinkActions` all implement their own overlay, dismissal, and focus behavior.

Examples:

- Command palette overlay: `ui/src/components/CommandPalette.tsx:30-54`
- New-tab popover dismissal: `ui/src/components/NewTabPopover.tsx:62-95`
- Add Project confirmation: `ui/src/components/ProjectDialogs.tsx:112-165`
- Add Worktree form: `ui/src/components/ProjectDialogs.tsx:309-373`

The visual language is related, but keyboard and modal semantics differ.

**Suggested solution**

Introduce narrowly scoped primitives:

- `ModalSurface`: focus trap, Escape, focus restoration, backdrop dismissal.
- `PopoverSurface`: anchored positioning, Escape, outside click, return focus.
- `MenuSurface`: roving menu-item focus and arrow-key handling.

Do not combine destructive confirmations, menus, and full-screen settings into one oversized abstraction.

### UX Improvement — `BrowserToolbar` bypasses the shared `IconButton`

The project has a consistent icon-button primitive with labels, titles, disabled behavior, and focus rings (`ui/src/components/ui/IconButton.tsx:12-34`). `BrowserToolbar` instead repeats button classes for every control (`ui/src/components/BrowserToolbar.tsx:90-180`).

This creates styling drift: toolbar buttons use `focus:border-primary` or no explicit focus-visible ring, while other shell actions consistently use `focus-visible:ring-ring`.

**Suggested solution**

Use `IconButton` for browser navigation, reload, zoom, focus, sync, and external-open controls. Extend the primitive first if the toolbar needs a smaller visual variant.

### Nit — unused Sidebar command-palette API

`SidebarProps` exposes `onOpenCommandPalette` at `ui/src/components/Sidebar.tsx:46`, but the component does not destructure or render it (`52-70`).

**Suggested solution**

Either add the intended command-palette action or remove the unused prop to keep the component contract truthful.

# 2. Drag and Drop UX & Split Resizing

## Strengths

The DnD model is well structured:

- Pointer and keyboard sensors are installed (`ui/src/components/TerminalSplitView.tsx:187-190`).
- Pointer drag has a 12px activation threshold, reducing accidental drags.
- Collision detection filters unknown/incompatible targets and orders valid collisions (`ui/src/components/TerminalSplitView.tsx:62-80`).
- Drop commands are represented as typed operations rather than direct state mutation (`ui/src/components/tab-dnd/tabDragTypes.ts:38-83`).
- Pane edges outrank group edges during tab drags (`ui/src/components/tab-dnd/tabDragTypes.ts:246-259`).
- All four split directions map consistently to tree direction and position (`ui/src/components/tab-dnd/tabDragTypes.ts:262-266`).
- Browser tabs dropped on terminal pane edges deliberately fall back to group-level splits rather than being inserted into a terminal-pane tree (`ui/src/components/TerminalSplitView.tsx:268-290`).

## Findings

### Warning — pane-center swap is shadowed by the group-body fallback

For pane drags, collision priority is:

1. `pane-edge`
2. `tab`
3. `group-body`
4. `pane-leaf`

See `ui/src/components/tab-dnd/tabDragTypes.ts:255-259`.

Every `pane-leaf` is nested inside `TabGroupDropSurface`, which registers the whole body as a droppable target (`ui/src/components/tab-dnd/TabGroupDropSurface.tsx:12-30`). Therefore, when the pointer is over the center of a pane, both `group-body` and `pane-leaf` collide, but `group-body` wins.

That makes the declared `swap-panes` center-drop behavior at `ui/src/components/tab-dnd/tabDragTypes.ts:230-237` effectively unreachable through normal collision selection. The likely result is detaching the pane to a tab/group instead of swapping panes.

**Suggested solution**

For pane drags, prioritize `pane-leaf` ahead of `group-body`:

```text
pane-edge → pane-leaf → tab → group-body
```

Add an integration-level collision test where both the leaf and its containing group body are under the pointer. Existing resolver tests call `resolveWorkspaceDropCommand` directly and do not expose this overlap.

### Warning — same-pane edge targets show valid feedback but resolve to no action

A pane dragged onto an edge of its own source leaf is rejected at `ui/src/components/tab-dnd/tabDragTypes.ts:202-204`.

However, every pane edge remains registered and displays the same “New split” feedback whenever `isOver` is true (`ui/src/components/tab-dnd/SplitEdgeDropZone.tsx:32-57`). The user can therefore see an apparently valid split target, drop, and get a no-op.

**Suggested solution**

Disable same-source pane-edge droppables while dragging, or render explicit invalid feedback such as “Already here.” Invalid targets should not use the primary split highlight.

### Warning — browser pane-edge fallback and terminal pane split share indistinguishable feedback

The visual always says “New split” (`ui/src/components/tab-dnd/SplitEdgeDropZone.tsx:51-57`). A terminal tab may be inserted relative to a specific pane, while a browser tab is instead split at the group level (`ui/src/components/TerminalSplitView.tsx:273-281`).

The resulting layout layer differs even though the preview is identical.

**Suggested solution**

Make feedback command-aware:

- “Split terminal pane”
- “Split tab group”
- “Move tab here”
- “Swap panes”
- “Create tab from pane”

This also makes fallback behavior easier to understand.

### UX Improvement — fixed 20% edge geometry is too small on tiny panes and too aggressive on large panes

Pane and group edges use fixed percentages:

- Left/right: 20% width.
- Top/bottom: 20% height, excluding the side 20% regions.

Citations:

- `ui/src/components/tab-dnd/SplitEdgeDropZone.tsx:63-72`
- `ui/src/components/tab-dnd/TabGroupDropSurface.tsx:48-54`

At the current 80px minimum pane size, a side target can be only 16px wide. On a wide pane, 20% can consume hundreds of pixels and trigger splits when the user intends a center/group drop.

**Suggested solution**

Use bounded dimensions, for example:

```css
width: clamp(24px, 16%, 72px);
height: clamp(24px, 16%, 72px);
```

Use a clearer central target for move/swap operations.

### Warning — pane resize hit area is only about 3px

The visible divider is one pixel, and its additional hit-area span extends only one pixel on either side (`ui/src/components/TerminalSplitView.tsx:982-991`). This is difficult to acquire, especially on high-resolution screens or with a trackpad.

The line itself uses `--terminal-divider` (`ui/src/components/TerminalSplitView.tsx:985`), which has approximately 2.22:1 contrast against `--terminal`; this is visually subdued for an interactive boundary (`ui/src/index.css:92-95`).

**Suggested solution**

- Keep a one-pixel visual line.
- Expand the invisible interaction area to 8-12px.
- Show a `ring`/`primary` hover and active state.
- Preserve the wider hit box even when the visible line stays minimal.

### Warning — split separators are not keyboard operable

Terminal/group split dividers expose `role="separator"` and `aria-valuenow`, but no `tabIndex`, keyboard handler, or min/max values (`ui/src/components/TerminalSplitView.tsx:973-993`).

The Sidebar separator supplies min/max/current ARIA values but is likewise pointer-only (`ui/src/components/Sidebar.tsx:295-305`).

**Suggested solution**

- Make separators focusable.
- Support Arrow keys for small increments.
- Support Shift+Arrow for larger increments.
- Support Home/End for min/max where appropriate.
- Add `aria-valuemin` and `aria-valuemax` to pane/group separators.

### UX Improvement — Sidebar hover feedback class cannot currently activate

The Sidebar resize line uses `group-hover:bg-ring/45`, but the separator parent has no `group` class (`ui/src/components/Sidebar.tsx:295-305`).

**Suggested solution**

Add the `group` marker to the separator or use direct hover selectors.

### UX Improvement — minimum pane size is too low for its own chrome

`MIN_PANE_SIZE_PX` is 80 (`ui/src/components/TerminalSplitView.tsx:50`). The pane toolbar can contain three 20px controls plus gaps and horizontal padding (`ui/src/components/TerminalSplitView.tsx:850-897`), leaving almost no usable terminal width.

The browser toolbar is much wider and is clipped by `BrowserPane`’s `overflow-hidden` container (`ui/src/components/BrowserPane.tsx:57-64`).

**Suggested solution**

Use content-aware minimums:

- Terminal pane: approximately 120-160px.
- Browser group/pane: larger minimum or responsive toolbar collapse.

# 3. CSS / Theming / Styling Health

## Design-system assessment

There is a real design system, not merely scattered colors:

- Geist variable font is loaded centrally (`ui/src/index.css:1-7`).
- Semantic base tokens are defined in `:root` (`ui/src/index.css:13-103`).
- Tailwind maps token RGB channels and opacity correctly (`ui/tailwind.config.js:2-50`).
- Sidebar, worktree, terminal, and status colors are semantically separated.
- Radius and shell dimensions are centralized in Tailwind configuration.
- Runtime appearance is propagated through `data-theme`, `data-accent`, and `data-density`.
- Dark/light and five custom accent selectors are defined in `settings-runtime.css`.

This is a good foundation.

## Findings

### Warning — active tabs ignore the configured accent color

The active tab uses an accent background but its underline is `bg-foreground` (`ui/src/components/tab-dnd/SortableTab.tsx:86-89`, `158-160`).

Changing the Ferryx accent color therefore affects browser icons and primary actions, but not the main active-tab indicator.

**Suggested solution**

Use a 2px `bg-primary` indicator, or a token specifically named `--tab-active-accent`. Preserve a non-color cue such as background and font weight.

### Warning — density settings barely affect most UI text

Density only changes root font size from 16px to 17px (`ui/src/settings-runtime.css:154-160`).

Most shell typography uses fixed pixel values such as:

- Tabs: `text-[12px]` (`ui/src/components/tab-dnd/SortableTab.tsx:87`)
- Sidebar metadata: `text-[9px]` (`ui/src/components/WorktreeList.tsx:98-105`)
- Palette headings/footer: `text-[10px]` (`ui/src/components/CommandPalette.tsx:73`, `119`)
- Project dialogs: `text-[10px]` through `text-[13px]` (`ui/src/components/ProjectDialogs.tsx:121-154`, `329-357`)

Fixed pixel text does not respond to the root-size density change.

**Suggested solution**

Define and use a typography scale in `rem`, for example:

- Caption
- Metadata
- Body-small
- Body
- Heading-small

Then make density selectors modify component spacing/height tokens as well as the root font size.

### Warning — low-opacity muted text fails normal-text contrast

The base muted colors themselves are reasonable:

- Charcoal: `#a1a1a1` on `#23262d`, about 5.86:1.
- Light: `#666b74` on `#f6f7f9`, about 5.0:1.

But components frequently reduce those tokens to 55-75% opacity. For example:

- New-tab “AGENTS” heading: `text-muted-foreground/60` (`ui/src/components/NewTabPopover.tsx:170-174`)
- Worktree branch/status metadata: `/75` (`ui/src/components/WorktreeList.tsx:98-105`)
- Project repository path: `/70` (`ui/src/components/ProjectDialogs.tsx:356`)
- Settings footer uses `/55` (`ui/src/components/SettingsDialog.tsx:162`)

In light mode, `text-muted-foreground/60` composites to roughly 2.36:1 against the background. These are also generally 9-10px labels, increasing legibility risk.

**Suggested solution**

Do not attenuate semantic text tokens with opacity. Add separate tested tokens such as:

- `--foreground-secondary`
- `--foreground-tertiary`
- `--foreground-disabled`

All readable metadata should retain at least 4.5:1 contrast.

### Warning — global `user-select: none` prevents useful text selection

The entire body disables selection (`ui/src/index.css:113-120`). This affects paths, branches, URLs, errors, and diagnostic content such as:

- Selected project path (`ui/src/components/ProjectDialogs.tsx:136-138`)
- Worktree repository path (`ui/src/components/ProjectDialogs.tsx:356`)
- Browser address/status text.
- Command-palette branch metadata.

**Suggested solution**

Apply `select-none` only to chrome, drag surfaces, and controls. Use `select-text` on URLs, paths, error messages, terminal-link dialogs, and diagnostic text.

### UX Improvement — typography and sizing still rely heavily on arbitrary values

The semantic color system is stronger than the spacing and typography system. Common one-offs include:

- `w-[72px]` traffic-light padding.
- `max-w-[420px]` dialogs.
- `pt-[12vh]` command palette.
- Numerous `text-[9px]` to `text-[15px]` values.
- Fixed 20% DnD geometry.

These values are internally repeated rather than represented by named design tokens.

**Suggested solution**

Extend Tailwind with named shell tokens before further UI work:

- `traffic-lights`
- `dialog-sm`
- `dialog-lg`
- `text-caption`
- `text-metadata`
- `drop-edge`
- `split-hit-area`

### Nit — MobileKeyDock references a nonexistent scrollbar utility

`MobileKeyDock` uses `no-scrollbar` at `ui/src/components/MobileKeyDock.tsx:54` and `73`. The defined utility is `.scrollbar-none` (`ui/src/index.css:132-138`).

**Suggested solution**

Replace `no-scrollbar` with `scrollbar-none`, or define one canonical alias.

### Positive — accent foreground contrast is correctly chosen

Every custom accent uses dark foreground text (`ui/src/settings-runtime.css:89-151`). Against `#0a0a0a`, the configured accents range from approximately 4.68:1 to 9.22:1. Purple is close to the threshold but passes.

The supplied/master icon was verified as:

- RGBA with transparent outer corners
- Visually consistent with the supplied black metallic squircle/crown asset
- Byte-identical to `ui/public/ferryx-icon.png`

## Findings

### Warning — legacy Orca logo remains in source assets

`ui/src/assets/orca-logo.svg` is a white Orca-era mark and is not referenced by the current UI source.

This is a cleanup and accidental-reuse risk, especially because current product branding is Ferryx.

**Suggested solution**

Remove the unused asset. If legacy migration documentation still requires it, move it outside the active UI asset directory and label it explicitly as archival.

### Warning — icon integrity test verifies only existence

The test named “ships the authentic master dark metallic squircle icon” only calls `existsSync` (`ui/src/assets/ferryx-icon.test.ts:5-9`). Any unrelated PNG placed at that path would pass.

**Suggested solution**

Test machine-consumed integrity rather than prose:

- Expected dimensions: 1024×1024.
- PNG/RGBA format.
- Expected SHA-256 or a committed source-to-derived-asset checksum.
- Public master equals source master.
- Derived dimensions exist for PWA/apple/favicons.

### Nit — legacy Orca terminology survives in implementation comments

The remaining non-test `Orca` references are branch-schema comments:

- `ui/src/components/Sidebar.tsx:324`
- `ui/src/components/WorktreeList.tsx:35`

These are not user-facing and may accurately describe backward-compatible branch names, so they are not a visible brand violation.

**Suggested solution**

If the branch namespace is intentionally still `orca/...`, clarify it as a legacy compatibility namespace. If the namespace has migrated, update both comments and parsing logic together rather than changing comments alone.

# 5. Accessibility & UX Edge Cases

## Keyboard navigation and focus

### Warning — tabs do not implement expected arrow-key navigation

The tablist is correctly marked with `role="tablist"` (`ui/src/components/TabBar.tsx:166`), and tabs use roving `tabIndex` plus `aria-selected` (`ui/src/components/tab-dnd/SortableTab.tsx:69-71`).

However, tabs only respond to Enter and Space (`ui/src/components/tab-dnd/SortableTab.tsx:79-84`). Standard tab behavior should also support:

- ArrowLeft / ArrowRight
- Home / End
- Optionally Delete for close

**Suggested solution**

Move tab keyboard handling to `TabBar`, calculate the next enabled tab, update focus, and activate according to the chosen automatic/manual activation model.

### Warning — interactive close control is nested inside a tab

Each `role="tab"` contains a focusable `span role="button"` for closing (`ui/src/components/tab-dnd/SortableTab.tsx:135-155`).

Nested interactive roles can produce confusing screen-reader and keyboard behavior.

**Suggested solution**

Render the tab activation button and close button as siblings inside a presentation wrapper. Keep the sortable listeners on the wrapper or a dedicated drag handle.

### Warning — context menu has ARIA roles without menu keyboard behavior

The tab context menu has `role="menu"` and `role="menuitem"` (`ui/src/components/TabBar.tsx:375-388`), but:

- It does not focus the first item.
- It has no arrow-key navigation.
- It has no Home/End or typeahead.
- It only listens for Escape and outside mouse-down (`ui/src/components/TabBar.tsx:353-366`).
- There is no keyboard equivalent for opening it from a focused tab.

**Suggested solution**

Implement a real roving-focus menu and open it with Shift+F10 / ContextMenu key.

### Warning — CommandPalette is not a complete keyboard command palette

The input receives focus and Escape closes it (`ui/src/components/CommandPalette.tsx:30-43`), but results are ordinary buttons with no highlighted active option, ArrowUp/ArrowDown movement, Enter-to-select, `listbox` semantics, or `aria-activedescendant` (`70-112`).

It declares `aria-modal="true"` but does not trap focus or restore focus on close (`48-54`).

**Suggested solution**

Use combobox/listbox semantics, maintain an active index, scroll the active result into view, trap Tab within the dialog, and restore focus to the opener.

### Warning — project dialogs lack consistent dialog semantics and focus isolation

The Tauri confirmation variant has `role="dialog"` but no `aria-modal` (`ui/src/components/ProjectDialogs.tsx:113-117`).

The fallback Add Project and Add Worktree forms have accessible names but no `role="dialog"` or `aria-modal` (`ui/src/components/ProjectDialogs.tsx:192-196`, `310-314`).

None of these surfaces implements a focus trap, Escape handling, or opener-focus restoration.

**Suggested solution**

Use the shared modal primitive described earlier. Connect headings with `aria-labelledby` rather than naming the dialog separately from its visible heading.

### Warning — hidden pane toolbar controls remain focusable

The pane toolbar is hidden with `opacity-0` and `pointer-events-none`, but remains rendered with dnd-kit draggable attributes and focusable child buttons (`ui/src/components/TerminalSplitView.tsx:846-898`).

Keyboard users can tab into invisible split/close controls. Conversely, the toolbar only becomes visible from mouse hover, not `focus-within`.

**Suggested solution**

- Reveal the toolbar on `focus-within`.
- Use `visibility: hidden`/`inert` when closed if it should be absent from tab order.
- Prefer an always discoverable pane actions button when multiple panes exist.
- Provide a separately labeled drag handle rather than making the entire toolbar draggable.

## Mobile key dock

### Warning — icon-only arrow buttons have no accessible name

The arrow buttons pass only an icon, with neither `aria-label` nor `title` (`ui/src/components/MobileKeyDock.tsx:97-101`, `131-145`).

The “More keys” button has a title but no explicit expanded state.

**Suggested solution**

Add labels such as “Left arrow,” “Up arrow,” and `aria-expanded={isExpanded}` to the utility toggle.

### Warning — modifier latch state is not announced

Ctrl and Alt visually change but do not expose `aria-pressed` (`ui/src/components/MobileKeyDock.tsx:75-85`, `132-142`).

**Suggested solution**

Set `aria-pressed` from the `active` prop.

### Warning — Ctrl+Alt combinations are mishandled

Both modifiers can be latched, but key dispatch uses `if ... else if` (`ui/src/components/MobileKeyDock.tsx:38-45`). If Ctrl and Alt are both active, only `ctrl-*` is sent, Ctrl is cleared, and Alt remains unexpectedly latched.

**Suggested solution**

Compose all active modifiers in a stable order, then clear both after the next non-modifier key.

### UX Improvement — touch targets are below recommended size

Keys are 38×32px minimum (`ui/src/components/MobileKeyDock.tsx:136`), below the commonly recommended 44×44 CSS-pixel touch target.

**Suggested solution**

Use at least 44px height and width, with visual content allowed to remain smaller.

### UX Improvement — no safe-area accommodation

The dock has no `env(safe-area-inset-bottom)` padding (`ui/src/components/MobileKeyDock.tsx:50-110`).

**Suggested solution**

Add bottom safe-area padding for standalone/mobile use.

## Overflow and clipping

### Warning — NewTabPopover can leave the viewport in narrow/right-side groups

The popover is absolutely positioned `left-0`, fixed at `w-80`, with no collision detection (`ui/src/components/NewTabPopover.tsx:90-96`).

In a narrow split group or group near the right edge, it can extend outside the viewport.

**Suggested solution**

Use viewport-aware anchored positioning and flip/alignment logic.

### UX Improvement — context-menu clipping uses guessed dimensions

The context menu clamps based on fixed assumptions of 200×260px (`ui/src/components/TabBar.tsx:372-380`). Its actual height varies with enabled actions and can exceed 260px.

**Suggested solution**

Measure the rendered menu and reposition it in a layout effect, or use a positioning library.

### Warning — BrowserToolbar does not degrade for narrow splits

`BrowserPane` clips overflow (`ui/src/components/BrowserPane.tsx:57-64`), while the toolbar always renders navigation, address, zoom, focus, sync, and external-open controls (`ui/src/components/BrowserToolbar.tsx:87-182`).

At narrow widths, controls will be clipped rather than collapsed into an overflow menu.

**Suggested solution**

Define toolbar breakpoints:

- Always show address and reload.
- Collapse zoom and diagnostics into a menu.
- Hide the percentage label first.
- Enforce a realistic minimum browser-group width.

# 6. Additional Functional UX Finding

### Warning — Browser Back/Forward can be enabled but inert

`BrowserToolbar` accepts optional `onGoBack` and `onGoForward` callbacks (`ui/src/components/BrowserToolbar.tsx:6-20`). The buttons are enabled from `tab.canGoBack` and `tab.canGoForward`, but invoke those optional callbacks (`90-107`).

`BrowserPane` does not accept or forward these callbacks (`ui/src/components/BrowserPane.tsx:6-13`, `57-60`), and `TerminalSplitView` only supplies navigation and reload (`ui/src/components/TerminalSplitView.tsx:657-663`).

Thus, if browser state marks Back or Forward as available, the corresponding button is enabled but does nothing.

**Suggested solution**

Add browser history commands to the container contract and wire them through:

```text
TerminalSplitView → BrowserPane → BrowserToolbar
```

Until handlers exist, disable the buttons based on both capability and callback presence.

### UX Improvement — browser zoom display starts at 100% regardless of browser state

`zoomFactor` initializes to `1.0` (`ui/src/components/BrowserToolbar.tsx:21-22`). `getBrowserState` is only used by the manual Sync action, and even then only the URL is copied (`76-84`), despite browser state containing `zoomFactor`.

**Suggested solution**

Initialize/synchronize zoom from browser state and update both URL and zoom during Sync.
