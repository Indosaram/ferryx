## Findings

**The headline: Orca has two independent binary layout trees; rorca has neither.**

| | Tree | Keyed by | Scope | Implementation |
|---|---|---|---|---|
| Outer | tab-group layout | `groupId` | per **worktree** | React `SplitNode` |
| Inner | terminal pane layout | `leafId` (UUID) | per **tab** | imperative DOM `.pane-split` |

**Per-tab splits are confirmed**, not inferred: `terminalLayoutsByTabId` is a record keyed by tab id, and focus is addressed by the `(tabId, leafId)` pair via `makePaneKey` → `` `${tabId}:${leafId}` ``.

**The reference screenshot is decisive.** I measured it rather than eyeballing: a 1px `#1b1b1b` divider at x=814, ratio exactly 0.5, spanning y=160→887. It stops *below* the tab strip and does not cut through it — both panes share one strip. That is unambiguously an inner per-tab pane split, which tells you which of the two trees rorca must build first.

**The gap is structural, not incremental.** `ui/src/state/layout.ts` models one global `{primaryTabId, secondaryTabId, split, nestedSplit}` — max ~3 panes, shared across all tabs. `normalizeLayout`'s invariants are incompatible with an n-ary tree, so I recommend rewriting the module rather than extending it, keeping the pure-reducer shape since its tests are already solid.

Three things I'd flag as easy to get wrong:
- **Inverted naming convention.** The DOM class `is-vertical` and the data-model `direction: "horizontal"` mean the *same* axis. Orca's own serializer bridges them. Pick one convention and never mix.
- **Collapse state is one flat `Set<string>`** of namespaced keys (`project-group:`, `repo:`, `lineage:`), not booleans on nodes. That's precisely what makes open/close state independent — collapsing a project leaves its worktrees' lineage state untouched.
- **WebGL must be disposed and re-attached across a rAF** when reparenting panes; the divider drag holds PTY resizes and commits once on pointerup. Miss either and you get lost GL contexts or `SIGWINCH` storms.

I deliberately recommend **deferring the outer tab-group tree** — the screenshot doesn't evidence it, and the model is designed so it can wrap the inner one later without touching `PaneNode`.

One caveat worth stating plainly: the reference image would not render at any resolution I tried, so my visual claims come entirely from programmatic pixel analysis (boundary detection and color sampling). The geometry and colors are exact; I have no read on tab *labels* or icon detail beyond that they're present and colored.
