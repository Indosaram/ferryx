I read this as a read-only architecture decision - I inspected the scoped implementation and direct tests and selected one minimal state model with exact integration and RED-test contracts.

## Bottom line

**Choose active-layout swapping, not a filtered view.** Keep one complete `LayoutState` active and park one complete `LayoutState` per inactive worktree; selecting a worktree atomically exchanges those layouts while terminal sessions remain project-global.

This preserves terminal pane trees without reconstruction, keeps browser tabs bound through `BrowserTab.worktreePath`, and fits the existing renderer and `layoutReducer` unchanged. Estimated effort: **Medium**.

## Action plan

### 1. Adopt this state model

In `ui/src/state/workspaceStore.ts`, change `WorkspaceState` to:

```ts
export type WorkspaceState = {
  worktrees: Worktree[];
  activeWorktreePath: string | null;

  /** Complete layout owned by activeWorktreePath. */
  layout: LayoutState;

  /** Complete layouts owned by inactive worktrees. The active path must not appear here. */
  inactiveLayoutsByWorktreePath: Record<string, LayoutState>;

  /** Project-global because PTYs survive worktree selection. */
  sessions: Record<string, TerminalSession>;

  unreadTabIds: Record<string, boolean>;
  unreadWorktreePaths: Record<string, boolean>;
  activityBySessionId?: Record<string, TerminalActivity>;
};
```

Required invariants:

1. `state.layout` is owned by `state.activeWorktreePath`.
2. `inactiveLayoutsByWorktreePath` never contains `activeWorktreePath`.
3. A tab ID occurs in exactly one owned layout and remains project-global.
4. `sessions` remains project-global; layouts only reference session IDs.
5. A browser tab's `worktreePath` equals the path of its owning layout.
6. A terminal tab may retain pane sessions from different worktrees after an existing pane merge. Its **whole `TabPaneLayout` remains indivisible** and is owned by the primary terminal session's worktree when migrating old data.

The current state has only one project-wide layout at `ui/src/state/workspaceStore.ts:28-34`. Sessions must not be moved into the per-worktree map: pane leaves already reference frontend-local session IDs through `LayoutState.layoutsByTabId`, documented at `ui/src/lib/types.ts:157-199`.

### 2. Make `SELECT_WORKTREE` swap complete layouts

At `ui/src/state/workspaceStore.ts:759-767`, replace the path-only update with an atomic swap:

1. Validate the target worktree.
2. Store the current `state.layout` under the old active path.
3. Load and remove the target path's parked layout, defaulting to `createLayoutState()`.
4. Set the target as `activeWorktreePath`.
5. Preserve the existing unread-clearing behavior.

Conceptually:

```ts
const inactive = { ...state.inactiveLayoutsByWorktreePath };

if (state.activeWorktreePath) {
  inactive[state.activeWorktreePath] = state.layout;
}

const layout = inactive[action.path] ?? createLayoutState();
delete inactive[action.path];

return {
  ...state,
  activeWorktreePath: action.path,
  layout,
  inactiveLayoutsByWorktreePath: inactive,
  // existing unread cleanup
};
```

Do **not** derive a filtered layout from one global `LayoutState`.

Causal justification:

- `normalizeLayout` treats `tabs`, `layoutsByTabId`, `tabGroups`, and `tabGroupLayout` as one closed ownership graph. It removes pane layouts outside `tabs` at `ui/src/state/layout.ts:592-631` and rebuilds/prunes groups from the same valid tab set at `ui/src/state/layout.ts:633-679`.
- Reducer operations mutate that complete graph, including group removal and split-tree collapse. A filtered view would therefore need a reverse reconciliation algorithm after every close, reorder, split, pane move, and normalization.
- Swapping retains the exact `LayoutState` object, so ratios, active groups, active leaves, tab ordering, pane trees, and session mappings remain unchanged.

### 3. Route layout actions to their owning worktree

Add small internal helpers in `workspaceStore.ts`:

```ts
getLayoutForWorktree(state, path)
updateLayoutForWorktree(state, path, reducer)
findTabOwnerPath(state, tabId)
listOwnedLayouts(state)
listWorkspaceTabs(state)
```

`findTabOwnerPath` must inspect the active layout and every parked layout. The owning layout is authoritative; do not infer ownership from an arbitrary pane session.

Update these integration points:

- `ADD_TAB_WITH_SESSION` gains `worktreePath`.
- `UPDATE_BROWSER_TAB`, `CLOSE_TAB`, `ACTIVATE_TAB`, `REORDER_TAB`, `RENAME_TAB`, `SET_TAB_PINNED`, pane operations, and tab-group moves use `findTabOwnerPath`.
- Pathless operations such as `SET_TAB_GROUP_RATIO` continue targeting the visible active layout.
- Async operations must retain their original target path. This prevents a terminal or browser completing after a worktree switch from being inserted into the newly selected layout.
- Last-tab replacement logic must use the owning layout's tab count, not the total number of project tabs.
- `SET_WORKTREES` must remove parked layouts for deleted paths and normalize each retained layout independently.

This is necessary because `ensureTabForWorktree` currently searches the one global tab list at `ui/src/state/workspaceStore.ts:214-224`, while `ADD_TAB_WITH_SESSION` currently always mutates `state.layout` at `ui/src/state/workspaceStore.ts:795-802`.

The existing terminal ownership functions must also traverse every owned layout, not just `state.layout`:

- `getTabSessionIds`: `ui/src/state/workspaceStore.ts:1030-1038`
- `isSessionReferencedOutsideTab`: `ui/src/state/workspaceStore.ts:1040-1042`
- `findTabIdForSession`: immediately after `ui/src/state/workspaceStore.ts:1067-1074`

That prevents closing a background tab or pane from incorrectly destroying a still-referenced PTY.

### 4. Preserve terminal pane splits exactly

No structural change is required in `ui/src/state/layout.ts`.

Each terminal tab already owns an independent pane tree and per-leaf session mapping through `TabPaneLayout`; `TerminalSplitView` resolves every rendered leaf through:

```ts
tabLayout.sessionIdsByLeafId[node.leafId]
```

at `ui/src/components/TerminalSplitView.tsx:640-650`.

Therefore:

- Move the whole `LayoutState` during worktree selection.
- Never repartition or regenerate `layoutsByTabId[tabId]`.
- Keep `sessions` global.
- On v1/v2 migration, assign a terminal tab to the worktree of `primarySessionId`; if missing, use the first valid mapped pane session; only then fall back to `activeWorktreePath`.
- If a migrated tab contains pane sessions from multiple worktrees, preserve the entire tree under that selected owner. Splitting the tab would alter the user's visible pane arrangement.

Existing direct tests already establish that the pane tree and PTYs are the state that must survive:

- Independent PTY creation: `ui/src/state/workspaceStore.test.tsx:177`
- Tab-group moves preserve pane trees and PTYs: `ui/src/state/workspaceStore.tabDrop.test.tsx:112`
- Pane-targeted moves preserve the source subtree and sessions: `ui/src/state/workspaceStore.paneDrop.runtime.test.tsx:107`
- Renderer consumes nested pane trees: `ui/src/components/TerminalSplitView.test.tsx:102`

### 5. Make browser ownership explicit

`BrowserTab.worktreePath` already exists but is optional at `ui/src/lib/types.ts:104-117`. Keep it optional only for old persisted/test inputs; normalize all live/restored tabs to a concrete path.

Current creation sends the active path to the native browser but omits it from the resulting React tab at `ui/src/state/workspaceStore.ts:510-536`. Change it to capture the path before awaiting native creation:

```ts
const worktreePath = stateRef.current.activeWorktreePath;
if (!worktreePath) return null;

const browserState = await createBrowser({ workspaceId, worktreePath, ... });

const browserTab: BrowserTab = {
  ...,
  worktreePath: browserState.worktreePath ?? worktreePath,
};
dispatch({
  type: "ADD_TAB_WITH_SESSION",
  worktreePath,
  tab: browserTab,
});
```

If the user switches worktrees while `createBrowser` is pending, the tab remains in the captured worktree's layout and must not force selection back.

Browser tabs need no terminal pane state beyond the existing placeholder leaf. `TerminalSplitView` already renders the active browser directly at `ui/src/components/TerminalSplitView.tsx:567-578`.

#### Version 3 serialization

`serializeWorkspaceState` currently serializes one layout at `ui/src/lib/sessionPersistence.ts:28-92` and collects session references from only those tabs at `ui/src/lib/sessionPersistence.ts:96-113`.

Instead:

1. Form all owned layouts from:
   - `[activeWorktreePath, state.layout]`
   - every `inactiveLayoutsByWorktreePath` entry
2. Normalize and serialize each independently into `layoutsByWorktreePath`.
3. Save `BrowserTab.worktreePath` in `PersistedBrowserTabState`.
4. Collect referenced terminal session IDs across **all** persisted layouts.
5. Continue storing terminal sessions once at the project/workspace level.

This preserves project-level persistence without duplicating PTYs per worktree.

#### Version 1/2 migration

The current format has one `PersistedWorkspace.layout` at `ui/src/lib/types.ts:380-386`.

For a v1/v2 input:

1. Deserialize tabs, pane trees, groups, and sessions using the existing compatibility logic.
2. Determine one owner path per tab:
   - Browser: persisted browser/tab `worktreePath`, otherwise `ws.activeWorktreePath`.
   - Terminal: primary session's `worktreePath`, then first valid pane session, then `ws.activeWorktreePath`.
3. For each owner, construct a complete subset `LayoutState` with its tabs and existing `layoutsByTabId`.
4. Pass each subset through `normalizeLayout`. Its existing pruning safely removes group references to tabs assigned to another owner while retaining each tab's pane tree.
5. Return the active owner's layout as `state.layout`; park the rest.
6. Do not write back during deserialization. The next normal save upgrades the session to v3.

Old browser ownership is inherently ambiguous because v2 serialization omits `worktreePath` at `ui/src/lib/sessionPersistence.ts:37-51`, and v2 deserialization also does not restore it at `ui/src/lib/sessionPersistence.ts:179-195`. Falling back to the persisted active worktree is the only deterministic migration available.

## Risks and mitigations

- **Legacy browser ownership is missing.** Deterministically assign v1/v2 browser tabs to the persisted active worktree; v3 records the real path.
- **Existing mixed-worktree terminal panes could be damaged by migration.** Assign the entire tab by primary session and preserve its complete pane tree; never split leaves across layouts.
- **Async operations can finish after selection changes.** Carry an explicit owner path or locate the tab's owning layout in every reducer action.
- **Inactive PTYs could be closed accidentally.** Keep sessions global and make all reference scans traverse active and parked layouts.
- **Tab IDs must remain project-global.** Preserve current UUID generation and enforce one-layout ownership during restore normalization.
