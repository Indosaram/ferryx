### 2. Bridge and API check

- `main.tsx` **does install the runtime bridge**.
- `SettingsDialog` appearance controls **do not use the same persistence API** as the bridge:
  - Dialog uses direct `localStorage` reads/writes at `SettingsDialog.tsx:273-293`.
  - Runtime uses `loadAppearanceSettings`/`saveAppearanceSettings` from `lib/appearanceSettings.ts`.
- Both currently use the same key, `ferryx.settings.appearance`, but only the shared API performs validation and dispatches `ferryx:appearance-settings`.

### 3. Mutually exclusive hypotheses

1. **Storage is unavailable or cleared** between sessions; startup correctly falls back to defaults.
2. **Invalid/corrupt persisted JSON or unsupported values** are normalized to defaults by `loadAppearanceSettings`.
3. **The dialog and runtime bridge use separate persistence implementations**, causing inconsistent state/event behavior, especially when another consumer relies on the shared appearance event/API.
4. **The desktop app is launching a different webview/storage origin/profile**, so the saved localStorage belongs to a different origin or is not retained.

### 4. Observed/reasoned root cause

The strongest code-supported cause is the **duplicate persistence path**:

- `SettingsDialog` writes directly to localStorage and never dispatches `APPEARANCE_SETTINGS_EVENT`.
- The runtime bridge starts through the shared API and normalizes/re-saves whatever it loads.
- The shared hook/API (`appearanceSettings.ts:112+`) is event-driven, while the actual dialog is not using it.

This is a real architectural inconsistency. However, the existing tests show that same-origin remount persistence works, so the code does **not** prove that ordinary desktop restart alone loses the value. If the key is retained in the same webview origin, startup should restore it via `main.tsx:8 -> settingsRuntimeBridge.ts:84 -> appearanceSettings.ts:51-60`.

### 5. Smallest write scope and failing-first test seam

Smallest likely fix scope: **only `ui/src/components/SettingsDialog.tsx` appearance state/update/reset logic**, replacing direct storage handling with the shared appearance API/hook. No startup or CSS changes are indicated.

Failing-first test seam:

- Extend `ui/src/components/SettingsDialog.test.tsx` appearance coverage to assert that changing a control dispatches `APPEARANCE_SETTINGS_EVENT` (or that a mounted `useAppearanceSettings` consumer updates).
- Existing persistence/remount test is at `SettingsDialog.test.tsx:284-320`; the missing seam is cross-consumer event synchronization.
