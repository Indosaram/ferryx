I read this as a read-only reducer/pane-tree diagnosis - I traced both movement paths and used narrow Vitest runs to identify the failing seam.

## Diagnosis

The layout reducer and pane-tree transition are **not the causal lane**. Manually dispatched pane-targeted moves work and preserve PTY ownership. The user-visible transition fails earlier because pane-edge drag support is only partially integrated into `TerminalSplitView` and `tabDragTypes`.

### Current action flow

**Working group-level terminal/browser movement**

1. Group edge/body/tab drop resolves to `move-tab-to-split` or `move-tab-to-group`.
2. `TerminalSplitView.tsx:232-250` invokes the corresponding callback.
3. `workspaceStore.ts:325-345` dispatches `MOVE_TAB_TO_SPLIT`, or `workspaceStore.ts:320` dispatches `MOVE_TAB_TO_GROUP`.
4. `workspaceStore.ts:937-950` delegates to `layoutReducer`.
5. `layout.ts:255-363` updates tab groups and `tabGroupLayout`; each tab’s pane tree remains attached to that tab.
6. This path works for terminal and browser tabs. Existing browser split/merge coverage passes.

**Intended pane-targeted terminal movement**

1. A pane edge should produce `pane-edge` drop data.
2. It should resolve to `move-tab-to-pane-split`.
3. `workspaceStore.ts:325-341` should dispatch `MOVE_TAB_TO_PANE_SPLIT`.
4. `workspaceStore.ts:951-963` calls `moveTabIntoPaneSplit`.
5. `tabPaneDrop.ts:56-102` remaps colliding leaf IDs, calls `splitLeafWithSubtree`, removes source-tab ownership, and merges session mappings.
6. `paneTree.ts:49-63` performs the immutable subtree insertion.

Steps 3-6 are implemented and passing. Steps 1-2 are currently broken.

## Concrete failing transition

Given `tab-source` and `tab-target`, with target pane `leaf-right`:

1. Drag `tab-source` onto the **left edge of `leaf-right`**.
2. Expected: dispatch a pane-targeted move and replace `leaf-right` with:
   ```text
   horizontal(source pane subtree, leaf-right)
   ```
   Then remove `tab-source` while retaining all source sessions in `tab-target`.
3. Actual:
   - No pane-edge droppable is rendered, so the overlapping group edge can win and create a separate tab group instead; or
   - If `pane-edge` data is supplied directly, it is rejected/unhandled, gets priority `100`, and resolves to no command.

Thus the exact-leaf transition never reaches the working store/reducer path.

## Root-cause candidates, ordered

1. **Most likely: incomplete pane-edge command routing**
   - `ui/src/components/tab-dnd/tabDragTypes.ts:85-99`  
     `isWorkspaceDropData` omits the declared `pane-edge` variant.
   - `ui/src/components/tab-dnd/tabDragTypes.ts:108-136`  
     The tab-drag resolver has no `pane-edge` case.
   - `ui/src/components/tab-dnd/tabDragTypes.ts:45-71`  
     `WorkspaceDropCommand` has no `move-tab-to-pane-split` command.
   - `ui/src/components/tab-dnd/tabDragTypes.ts:172-177`  
     Pane edges receive fallback priority `100`, below overlapping group edges.

2. **Pane-edge UI exists but is never mounted**
   - `ui/src/components/tab-dnd/PaneEdgeDropZones.tsx:11-24` defines the four zones.
   - `ui/src/components/TerminalSplitView.tsx:739-750` renders each pane leaf without `PaneEdgeDropZones`.
   - No reference to `PaneEdgeDropZones` exists in `TerminalSplitView.tsx` or `TerminalPane.tsx`.

3. **Executor lacks the new command**
   - `ui/src/components/TerminalSplitView.tsx:236-257` has no `move-tab-to-pane-split` branch capable of forwarding `{tabId, leafId}` as the optional `targetPane`.
   - The downstream callback is already ready at `workspaceStore.ts:325-341`.

The most likely single defect is therefore an **unfinished pane-edge DnD integration upstream of the state reducer**, not an incorrect pane-tree state transition.

   RED isolates `tabDragTypes.ts:45-71,108-136,172-177`.

3. **Zone mounting**
   Render one pane and assert four descendants with `data-dnd-type="pane-edge"`.  
   RED isolates `TerminalSplitView.tsx:739-750`.

   Keep the existing direct `moveTabToSplit(..., {tabId, leafId})` store test green. It proves the same intended command succeeds once it reaches `workspaceStore`.

The current existing tests already provide items 2-4, though the combined resolver test should ideally be split because its priority assertion fails before command resolution is checked.
