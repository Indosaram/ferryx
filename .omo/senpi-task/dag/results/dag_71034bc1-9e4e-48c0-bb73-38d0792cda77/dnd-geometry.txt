I read this as a read-only drag/drop geometry and split-composition diagnosis - I inspected the screenshot and design system, traced source/target payloads through the reducer and renderer, and ran the focused tests without editing files.

## Diagnosis

### Primary finding

The screenshot does **not** show a free-floating coordinate error.

The highlighted `New split` rectangle exactly matches the terminal group’s configured **top-edge hit target**:

- Terminal group body: approximately `x=292..813`, width `522px`
- Top zone CSS: 20% left/right inset and 20% height
- Expected geometry:
  - left: `292 + 522 × .20 = 396.4`
  - right: `813 - 522 × .20 = 708.6`
  - width: `313.2px`
  - body height approximately `818px`; 20% is `163.6px`
- Screenshot rectangle: approximately `x=396..709`, `y=70..233`

That is an exact match for:

```tsx
left-[20%] right-[20%] top-0 h-[20%]
```

at `ui/src/components/tab-dnd/TabGroupDropSurface.tsx:52`.

The apparent misalignment comes from two separate visuals:

1. `DragOverlay` follows the pointer and displays `main (2)`.
2. The edge target is parent-relative and highlights a 20%-deep hit region.

The edge region is **not a preview of the resulting 50/50 split**. The reducer creates a split with default ratio `0.5`, while the indicator displays only 20% of the target height. That semantic mismatch can make the preview look wrongly sized even though its coordinates are correct.

### Rendered composition finding

The existing terminal/browser layout appears to be:

```text
horizontal root
├── terminal tab group: main, main (2)
└── browser tab group: Browser
```

Dropping `main (2)` on the terminal group’s top edge does not split the entire root. It replaces only the targeted terminal group leaf:

```text
horizontal root
├── vertical nested split
│   ├── new group: main (2)
│   └── existing group: main
└── browser group: Browser
```

Therefore, the browser remaining independently rendered across the full right-hand side is expected from the current reducer semantics. This is the strongest explanation for the screenshot’s composition.

There is no terminal-versus-browser branch in the whole-tab split reducer. Both tab kinds take the same group-tree path; only the targeted group node determines where nesting occurs.

### 8. Reducer tree mutation

`ui/src/state/layout.ts:315-363`

The reducer:

1. Finds the source tab and its source group.
2. Finds `groups[action.targetGroupId]`.
3. Removes the source tab from its old group.
4. Creates a new single-tab group.
5. Calls `splitTabGroupLeaf` with the exact target group ID.
6. Focuses the new group.

`ui/src/state/layout.ts:736-760`

`splitTabGroupLeaf` recursively finds only the matching group leaf and replaces it with:

```tsx
{
  type: "split",
  direction,
  first: position === "first" ? added : target,
  second: position === "first" ? target : added,
  ratio: 0.5,
}
```

It does not promote the split to the root. This is why targeting the terminal group leaves the browser sibling untouched.

### 9. Nested rendering

`ui/src/components/TerminalSplitView.tsx:372-415`

`TabGroupLayoutRenderer` recursively renders every split node as a flex row or column.

`ui/src/components/TerminalSplitView.tsx:383-391`

- Horizontal node → `flex-row`
- Vertical node → `flex-col`
- First child gets the stored percentage
- Second child gets remaining space

Thus a vertical split inserted beneath the terminal side of an existing horizontal terminal/browser root renders exactly as a nested split on the left.

### 10. Browser rendering distinction

`ui/src/components/TerminalSplitView.tsx:578-604`

An active browser tab renders `BrowserPane`; a terminal tab renders `PaneRenderer`.

`ui/src/components/BrowserPane.tsx:24-47`

The browser body is a native child webview whose bounds are synchronized from the placeholder DOM rectangle.

`src-tauri/src/ipc/browser.rs:97-118`

Applies those logical bounds via `webview.set_bounds`.

This introduces a secondary integration risk: native child webviews are not ordinary DOM stacking content. CSS `z-index` cannot guarantee that a React drop indicator appears above the browser surface, and pointer movement over the child webview may not behave like movement over terminal DOM. The screenshot does not require this hypothesis—the browser correctly remains a separate sibling—but browser-edge drag behavior needs native integration coverage.

## Source/target ID assessment

For the currently working whole-tab/group path, there is no evidence of source or target ID corruption:

- Source data contains `tabId`, `groupId`, and `index`.
- Target data contains the exact target `groupId` and edge.
- No ID string parsing occurs after registration.
- Existing pointer resolver and store tests pass.
- Terminal and browser tabs share the same payload format.

The incomplete pane-edge path is different:

- `PaneEdgeDropData` is declared.
- `PaneEdgeDropZones` exists.
- The zones are not mounted.
- `isWorkspaceDropData` does not accept `"pane-edge"` at `tabDragTypes.ts:85-99`.
- `resolveWorkspaceDropCommand` does not handle `"pane-edge"`.
- `dropPriority` returns `100`, excluding it from collisions.
- Current pane drag data uses `leafId`, while the pane-handle runtime tests expect `sourcePaneId` and `sourceSessionId`.

Thus pane-edge events cannot currently reach any reducer action.

## Concrete hypotheses, ranked

1. **Confirmed: hit-target versus result-preview mismatch.**  
   The indicator is correctly positioned but represents a 20% hit target, while the resulting split is 50/50. This explains the undersized overlay.

2. **Confirmed: nested target-leaf rendering.**  
   A drop on the terminal group splits only that group, not the existing terminal/browser root. This explains why the browser remains unchanged on the right.

3. **Rejected for the whole-tab screenshot: bad source/target IDs.**  
   The whole-tab IDs and payload path are coherent, and related tests pass.

4. **Confirmed incomplete implementation: pane-edge IDs/data.**  
   Pane-edge targets are declared but neither mounted nor recognized by collision/command resolution.

5. **Possible browser-specific integration issue.**  
   Native webview stacking and event routing could prevent indicators or collisions over the browser body. This requires a Tauri-level test; the screenshot alone does not demonstrate it.
