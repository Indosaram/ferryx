## The code-level gap found, and closed

The audit of the capture path found that `runSplitCancelScenario` was the **one** adapter with no owned-window
capture and no inspection handshake, so a cancelled split could never produce a viewed screenshot even if the
scenario passed. The three sibling adapters all had it.

**Closed in this session** at `9be5eb3f` (on main). Closing it required the adapter **and its nine call sites**,
because every cancel test is a success path: the sibling adapters' tests only exercise rejection paths and so
never reach their capture block. Evidence:

- Frozen gate with the change: **98 passed (98)**.
- Mutation (adapter tail removed, tests kept): **1 failed | 97 passed** — exactly the cancel adapter test red, so
  the new coverage is load-bearing rather than decorative.

## Why F3 still cannot pass

The capture mechanism now exists for all four split adapters, but F3 audits **viewed screenshots that were
actually produced by a native run**, and the native matrix has produced none:

1. Every native run in the matrix stopped **upstream of the capture** — the split step never settled, so the
   scenario never reached its capture block. That is an execution fact, not a source property.
2. Task 10 (packaged smoke) never ran, so there are no packaged bytes for the "exact packaged smoke" clause.
3. The mac half of the platform coverage is **parked by the user's instruction**.

**So F3's remaining work is execution, not code**: run the native matrix on a host where the split step settles,
produce the screenshots, and re-audit. The code path that would produce them is now wired and mutation-proven.
