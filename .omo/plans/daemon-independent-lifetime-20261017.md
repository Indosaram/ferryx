# daemon-independent-lifetime-20261017 - Work Plan

## TL;DR (For humans)
**Who this is for and what changes for them:** Anyone running terminals or agents in Ferryx. After this work, quitting the app, force-quitting it, reopening it, or installing an update no longer kills running terminals; they come back exactly as they were.

**What you'll get:** The background terminal service runs on its own, started by the operating system rather than by the app, on macOS, Linux and Windows. The app never kills it just because it is slow to answer. Updates hand terminals over safely or leave the old service running. Tests check that the actual shells survive, not just that their names are still listed.

**Why this approach:** The service currently runs from inside the app package, and the app restarts it when a connection check fails. Both can kill live work. Orca avoids this by giving its terminal host its own copy and its own OS registration, and by refusing to stop a host it cannot verify. This plan does the same.

**What it will NOT do:** Survive a reboot or logout, or a crash of the service itself. Touch the installed release app or your live sessions during testing. Explain the earlier unexplained shutdown signal.

**Effort:** XL
**Risk:** High - changes how the terminal service starts and upgrades on three operating systems
**Decisions to sanity-check:** This work does not bump the daemon protocol; it adds a frozen control channel so any later version can still ask an older service to hand over, retire once idle, or stop. An older service from before this change keeps working with the new app and is replaced only after it exits by itself. SSH and paired terminals are never moved during an update: the old service keeps them until they close. On Windows, an update that changes the service protocol leaves the old service running until its terminals close or you press "Restart terminals now", because Windows cannot move terminals between services; tests run only on an isolated debug build.

Your next move: start execution separately (e.g. /ulw-execute) when you want it built. Full execution detail follows below.

### Must have
- One baseline revision recorded at execution start; every reference below (HEAD 9b6c9338 line numbers unless marked otherwise) is re-validated against it before editing.
- Owner admission returns exactly one of Alive, Unknown, Absent from the truth table in todo 2, evaluated while holding the inter-process admission lock; an ordinary start (GUI setup, client connect, detached fallback, Windows mismatch path) happens only on Absent, inside that lock.
- The only start while an owner is Alive is a HandoverCandidate authorized by that owner's own upgrade request (todo 8): it holds no daemon lock, binds no public endpoint and accepts no client before commit, and exits 0 on any failure or expiry.
- A frozen, version-stable control channel (todo 15) through which any GUI version can read inventory, request upgrade, and request a count-confirmed shutdown; DAEMON_PROTOCOL_VERSION is not bumped by this plan.
- SSH/paired sessions across upgrade: never moved or re-created; the predecessor keeps serving them after commit (draining, routed through the successor) and exits only when the last one closes; uncertain writes are never replayed.
- macOS release ships a complete signed helper bundle (Contents/Helpers/Ferryx Daemon.app) built and signed at packaging time; runtime staging copies it byte-for-byte and verifies its signature, never constructs or edits a bundle.
- Immutable runtime copy outside the GUI install per platform, keyed by generation key <version>-<sha256 first 8 hex> of the staged executable; never overwritten while any process runs from it.
- One OS-owned job per generation key (launchd / systemd --user / per-user scheduled task); only the newest generation autostarts at login.
- Legacy single-job migration that never stops an Alive or Unknown legacy owner.
- Unix upgrade keeps the predecessor fully usable until the successor (started by its own generation job) commits ownership of the local PTYs; any failure leaves the predecessor serving everything; after commit the predecessor keeps serving its SSH/paired sessions until they close.
- Windows: the live owner is never shut down, terminated or replaced without an explicit user action naming the number of terminals that will end.
- Live-session inventory: local PTY child pid + start time; SSH/paired host-scoped remotePid; reader and connection state.
- Regression tests written first (user-confirmed strategy), then isolated debug-bundle QA Q00-Q13 with a precondition proving the daemon runs under the QA OS job.

### Must NOT have (guardrails, anti-slop, scope boundaries)
- No touching, quitting, replacing or signalling the installed release app, the live daemon, or live sessions, on any host. QA uses only isolated debug bundles with their own bundle id, label, socket, data and session dirs.
- No pattern-matched process kills; teardown kills only PIDs recorded at spawn and re-checked by executable path and start time.
- No launchctl bootout/unload, systemctl stop/restart, schtasks /End or kill against a job whose owner is Alive or Unknown.
- No kickstart -k, and no kickstart/reload used to "adopt" a running successor (plain kickstart is allowed only for a RegisteredIdle job with an Absent owner, todo 4); no POSIX_SPAWN_SETEXEC, process-group tricks or env scrubbing presented as GUI-independence.
- No unconditional CREATE_BREAKAWAY_FROM_JOB; no Windows ConPTY transfer claims.
- No change to SIGTERM exit codes as a substitute for keeping PTYs alive.
- No per-PTY owner process layer, reboot/logout continuity, daemon crash survival, provider cold-resume, automatic replacement shells, or production rollout.
- No restoring, unstaging or reverting foreign working-tree or index changes (AGENTS.md multi-session rules).
- No redesign of UI retry/transport (owned by .omo/plans/consistent-session-recovery*); integrate with it via regression tests only.
- No fixed sleeps or PID polling loops in new tests; no claim about the 2026-10-17 SIGTERM sender.
